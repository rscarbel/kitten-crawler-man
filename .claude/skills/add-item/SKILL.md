# Add an Item

Master registry: `src/core/items/defs/ItemDefs.ts`. Items are ids in the `ItemId` union with an entry in `ITEM_DEF: Record<ItemId, ItemDef>`. Bag and hotbar slots hold spread copies of a def plus `quantity` (`InventoryItem`); anything that must be current — `category`, `wearer`, `look`, `weapon` — is read off `ITEM_DEF`, never off a slot.

## `ItemDef` shape

Always: `id, name, category, stackable, canHotlist`, plus a line in `ITEM_PRICES` (`src/economy/itemPrices.ts`) giving its base price and pricing category — the compiler refuses an item without one. Optional on any item: `description`, `statBonus: Partial<Record<StatId, number>>` (`health`, `melee`, `magic`, `evasiveness`, `ranged`, `explosivesHandling` — `ALL_STATS` in `src/core/party/stats.ts`; one health is one max HP), `delivery` (a non-weapon item that deals damage: `'spell'` or `'thrownExplosive'`, which names the stat it scales with in its tooltip), `abilityId` (tomes), `skillId` (skill books), `explosivesHandlingLevels`, `drinkable`, `edible`, `menuUseLabel`, `isQuestItem`, `canDrop`, `unsellable`, `lootRecipient`, and the worn-gear effects (`regenMultiplier`, `resistances` (`'magic'` is turned aside centrally for any `DamageSource` with `magic: true`, by a share that grows with the wearer's Magic), `fairyImmunities`, `cancelsMomentum`, `skillLevelBonus`, `meleeOnlyStatBonus`). `description` is flavour only: what an item does is generated from its data (`describeItemEffects` in `src/ui/itemEffectLines.ts`, `wornGearSummary` in `gearRules.ts`), so never write a mechanic into it.

`ItemDef` is a union over what the item is, and the compiler holds each shape:

- **Armour** — `type: 'armor'`, `equipSlot`, `equipSubSlot`, `wearer: 'human' | 'cat' | 'both'` and `look` (required; see below).
- **Weapon** — `type: 'weapon'`, `equipSlot: 'Weapon'` / `equipSubSlot` (`Main` for the human's hand weapons, `Claws` for the cat's claws), `wearer`, and a `weapon` stat block. No `look`: a hand weapon looks like its `weapon.heldVisual`, claws like their `weapon.garment`. Two `Weapon` pieces are armour, not weapons: a relic (`Weapon:Relic`) carries a `relic` trait and is drawn at the shoulder by `GearSystem`, so its `look` is `RELIC_LOOK` (`{ kind: 'none', reason }`) for both crawlers; the human's off-hand buckler (`Weapon:Off`, `OFF_HAND_KEY`) is armour whose `look` is an `OffHandLook` (`BUCKLER_LOOK`, a held visual in the `offHandHeld` archetype) and whose block is the `frontalBlock` trait.
- **Gear fields** (armour and weapons only) — `rarity: Rarity` (required; `src/core/items/defs/rarity.ts`), `set?: GearSetId` (`src/gear/sets.ts`) and `traits?: GearTrait[]`: every mechanic beyond the plain fields is a trait (`src/gear/traits.ts`), described, scored and run by its handler in the complete `GEAR_TRAIT_HANDLERS` record and fired through the one entry point per hook in `src/gear/gearHooks.ts` (`landGearProcs` in `CombatSystem` for hits, `GearSystem` for ticks). Never check an item id in combat or player code; give the item a trait. Per-item memory (awakening kills, a curse's binding, once-per-floor flags, recharges) is `Player.gear` (`GearState`), saved in `PlayerSnapshot`. Every gear id also needs its sources in `GEAR_SOURCES` (`src/loot/gearPools.ts`), a complete record that excludes `dev_*` items.
- **Tool** — `type: 'tool'` with `tool: { kind, tier }` and `heldVisual` (the look a worker swings). See tools below.
- **Everything else** — `type: 'consumable'` or none; may not carry `wearer`, `weapon` or `look`.

How anything looks on a crawler — a garment, a held visual, the `look` field — is the `add-gear` skill. Read it before giving an item a look.

## End-to-end checklist

1. **Define**: add the id to the `ItemId` union and an entry to `ITEM_DEF` in `src/core/items/defs/ItemDefs.ts`.
2. **Icon** and **category**: fill in the item's `category` and add its painter to `ITEM_ICONS` (`src/ui/icons/itemIcons.ts`, the registry); typecheck forces both. New painters go in `src/sprites/art/itemIcons/`, painted in a unit square with the helpers in `iconPaint.ts` (`paintIconArt`, `paintForm`, `litFill`, `offsetShade`, `glint`); `npm run render:equipment-icons` shows them at slot size. Widgets draw it through `itemSlot`; code outside the widget kit (loot, reward fly-ins) uses `drawItemIcon` (`src/ui/icons/drawItemIcon.ts`).
3. **Use behavior** (if activatable): add a branch in `activateHotbarSlot` (`src/systems/kits/hotbarActions.ts`) — the single dispatch hub keyed on `slot.id` / `slot.abilityId`, shared by every scene with a hotbar. An item only one scene can honour goes in that scene's `trySceneSlot` instead. There is **no generic consume-on-use**: call `inventory.removeOne(id)` explicitly, apply the effect, play a sound, and emit an EventBus event if other systems care. Number keys 1–8 route here via `GameplayInputHandler`.
4. **Equipment** (armour or a weapon): set `type`, `equipSlot`, `equipSubSlot`, `wearer`, and `look` (armour) or `weapon` (weapons), plus any `statBonus`. Equip/unequip/drop is handled generically by the inventory screen, `MenusKit.resolvePendingInventoryActions` and `EquipmentManager` — no per-item code. Equipment is tracked by ItemId keyed on `"Slot:SubSlot"` (`EQUIP_SUBSLOTS`). The visual half — the garment or held visual and its gates — is `add-gear`.
5. **Loot** (if dropped by mobs): add to the base drop table in `Mob.rollLootItems` (`src/creatures/Mob.ts`) or override `rollLootItems` in a specific creature (see `Goblin`'s dynamite). `LootSystem` handles ground TTL and proximity/click pickup automatically. Boss drops flow through the `mobKilled` handler in `DungeonScene`. Gear never goes in a drop table: it declares its sources in `GEAR_SOURCES` (below).
6. **Price and shop**: the price is a line in `ITEM_PRICES` (`src/economy/itemPrices.ts`): `base` coins and a pricing `category`. To stock it, add a `CatalogLine` with every field stated: `item`, `normalStock`, `label` (the item's own name, or the shop's brand for it), `desc` (the line the shop card shows), `bundle` (`null` for a single unit) and `gate` (`null` for a line that is always stocked) to a shop in `SHOPS` (`src/economy/shops.ts`). Never put a price on a catalog line: a shop that charges more says so with `markup`, `categoryMarkup` or `itemMarkup`, and one that buys a category back at 75% instead of 50% lists it in `specialties`. Stock moves price both ways and restocks globally; the engine is `src/economy/pricing.ts` and its header explains the whole chain. A coin fee for an effect rather than an item goes in `SERVICE_PRICES` (`src/economy/servicePrices.ts`). Check with `npm run report:prices` (`-- --item <id>`), in game with `?prices`; `npm run verify:shop-pricing` guards against buy/sell arbitrage. Buying already guards on coins; the bag never fills, so a purchase always lands.

## Stats, scaling, skill books and proficiency

- **Stats.** Both crawlers carry the six stats in `ALL_STATS` (`src/core/party/stats.ts`). A gear `statBonus` is in stat units, the same for either wearer (one health is one max HP). A stat _point_ (a level-up, a Drill Yard drill, a stat-boost potion) is worth each crawler's gain in `STAT_GAIN_PER_POINT` (Ryan 2 health a point, Belle 2 evasiveness), read through `Player.statGainPerPoint`; anything that grants points goes through it, never raw HP or dodge. A table over stats is a `Record<StatId, …>`; never hard-code a list of stat names.
- **"Scales with".** An item that deals damage names its delivery (its `weapon.delivery`, its own `delivery`, or its ability's `delivery`), and `DELIVERY_STAT` maps that to the stat it grows with. The tooltip's "Scales with <Stat>" line (`scalingLine` in `src/ui/itemEffectLines.ts`) is derived from it, so a new weapon gets the line with no text written. Never scale an item's damage by a stat inside its own code.
- **Damage tags.** A weapon's required `family` is the tag its hits carry (`weaponHitTags` in `src/core/combat/damageTags.ts`); spells carry `'magic'`, burns `'fire'` and blasts `'explosion'`. The proficiency skills read those tags, so a new family is a new `WeaponFamily` member and, if a skill should boost it, an entry in that skill's `PROFICIENCY_SKILL_TAGS`.
- **Skill books.** A skill's book is `skill_book_<skillId>` (the `SkillBookId` type is derived from that pattern), with `skillId`, an `ITEM_ICONS` painter, an `ITEM_PRICES` line in the `tome` category, and "only the Cat/Human can learn" text that follows the skill's `eligibleFor`. Reading one unlocks the skill or raises it a level. Books drop only from creatures that lived by the skill: the creature calls `maybeDropSkillBook(items, pool)` (`src/creatures/skillBookDrop.ts`) with its `SkillBookPoolId`, and `SKILL_BOOK_POOLS` (`src/loot/skillBookPools.ts`) is the one weighted table of which books each pool holds. `SKILL_BOOK_DROP_CHANCE` alone decides whether a book drops, so adding a book to a pool never makes books more common; give a new book a place in a pool rather than a new creature drop.
- **Proficiency skills** (`PROFICIENCY_SKILL_IDS` in `src/core/skills/proficiency.ts`: Swordsmanship, Archery, Clawmanship, Magic Eye, Mechanical Fist, Blunt Proficiency, Pyro's Touch, Demolitionist) level to `PROFICIENCY_MAX_LEVEL` from tagged hits and from books, and share `proficiencyEffect(level)`. The standard skills (9 Lives, Cat-like Reflexes, Pugilism, Iron Stomach, Powerful Strike) keep their own five-level cap. Gear lifts a skill with `skillLevelBonus` (a gauntlet's Mechanical Fist levels), read through `Player.effectiveSkillLevel`.

## Food, tools, resources and ground pickups

- **Food.** `edible: true` gives the bag an "Eat" lead option (`leadOptionFor`) and the hotbar an `edible` branch; both call `MenusKit.eatFood`, the one eating path. The rules per food are pure functions in `src/core/items/consumables/foods.ts` (`eatHamburger`, `eatHollowStew`, add yours to `eatFood`) returning an outcome that `MenusKit` turns into sound, toast and bus events. A food that heals like a potion goes through `Player.usePotion` so it shares the potion cooldown; `firstHealingConsumable` is what the companion's auto-heal asks.
- **Tools.** `type: 'tool'` with `tool: { kind, tier }`, `canDrop: false`, not hotlistable, never equipped or sold, never consumed. Tiers are party state: `PartyTools.grantStarterTools` / `PartyTools.upgrade` (`src/core/items/gathering/PartyTools.ts`) swap the item **in place, in the same slot**, in both crawlers' inventories. Each tier's item (and Merrit's `quest_scythe`) names the `heldVisual` it is swung with, resolved by `workingToolHeldVisual`; `npm run verify:held-visuals` fails a tool item without one. A tool's extra bag actions (Summon Thrall) come through `InventoryActions.extraContextOptions` (`src/ui/screens/inventory/InventoryActions.ts`, on `MenusKit.inventoryActions`), not hard-coded in the inventory screen.
- **Resources** (`wood`, `stone`, `wood_board`, `rope`) go into the gathering crawler's own bag; every spend counts both bags through `src/core/items/gathering/partyResources.ts` (`partyCount`, `canAfford`, `spend`, `applyDiscount`), taking from the active crawler first.
- **Ground pickups.** An item that should lie visibly on the ground and be collected all at once with Space is a `GroundPickupKind` in `src/systems/GroundPickupSystem.ts`, mapped to its `ItemId` in `PICKUP_ITEM` and spawned with `groundPickups.spawn(kind, cx, cy, count)` (on `DestructionKit`). One press takes every pickup in reach.

## Equipment: wearers, held slots and weapons

- **Wearer.** `wearer` is required on armour and weapons and says who may equip it; `EQUIP_SUBSLOTS` (per crawler) says which sections and sub-slots each crawler has, and `EquipmentManager.canEquip` checks both (`wearerAllows`, `crawlerHasSection`). It also routes `!give` and reward splits: a reward split hands a one-crawler item to that crawler, and `lootRecipient` names the crawler for a signature drop either could wear (the Scrapmail Vest, `wearer: 'both'`, goes to the human).
- **Look.** Every armour item declares `look`: a garment per crawler it allows (`{ kind: 'garment', garment }`, or `{ human, cat }` for `'both'`), an off-hand shield's `{ kind: 'offHand', heldVisual, heardAs }` (`BUCKLER_LOOK`), or `{ kind: 'none', reason }` where nothing can draw it on the figure (`RELIC_LOOK` in `src/gear/catalogue.ts`). A trinket is a ring on his hand and a charm on her collar: `{ human, cat }` garments. Never leave gear silently invisible. Details in `add-gear`.
- **Sections.** `EQUIP_SUBSLOTS` is per crawler: the human has `Weapon` (`Main`, `Off`, `Relic`), `Head` (`Hat`, `Face`, `Neck`), `Torso` (`Shirt`, `Jacket`, `Back`), `Legs` (`Pants`, `Knees`), `Hands` (`Gloves`), `Feet` (`Shoes`) and `Trinkets` (`Trinket 1`, `Trinket 2`); the cat has `Weapon` (`Claws`, `Relic`), `Head`, `Torso`, `Feet` and `Trinkets`, with her own doll labels (`subSlotLabel`: Collar, Vest, Coat, Cloak, Booties). Shared gear fits by sub-slot id. A trinket declares the family `Trinket` and lands in either slot. The human's main hand is `MAIN_HAND_KEY` (`Weapon:Main`); always go through it.
- **Weapon stat block** (`src/core/items/equipment/weapons.ts`): every block a required `family` (`WeaponFamily`: the kind of weapon, which its hits carry as a damage tag for the proficiency skills); `MeleeWeaponStats` — `delivery: 'melee'`, `damageMultiplier` (times his bare-arm blow), `reachTiles` (`HUMAN_ARM_REACH_TILES` for arm's length), `heldVisual`, optional `onStrike` proc, optional `awakenedHeldVisual` — or `SlingWeaponStats` (`delivery: 'sling'`, `heldVisual`) — or, for the cat, `ClawWeaponStats` (`delivery: 'claw'`, `damageMultiplier` on her bare swipe, `reachBonusTiles`, `trail` colour or null, `garment`), read through `wornClaws` (`src/gear/gearHooks.ts`). Every melee weapon swings through `strikeWithWeapon` in `CombatSystem.ts`; a special effect is a proc registered in `CombatKit`'s `weaponProcs` (`add-gear` has the steps). `weaponStatsOf(id)` reads a hand weapon's block. Never tune the existing numbers.
- **Draw and stow.** A weapon in the hotbar is drawn rather than spent: `activateHotbarSlot` sends any item with a stat block to `HumanPlayer.toggleWeaponDrawn` (equipping it in `MAIN_HAND_KEY` first), which plays the weapon's draw or stow rows; the sound rides `equipmentChanged`, so every equip route plays it; a refusal buzzes. The main hand is the drawn weapon, so equipping one from the doll draws it. Read what he holds through `mainHandWeaponId`, `drawnWeapon`, `drawnMeleeWeapon` and `hasSlingDrawn` — never by checking item ids.
- **Saves.** `PlayerSnapshot` stores equipped entries as `[key, id]` pairs and bag/hotbar slots as `{ id, quantity }`. `parsePlayerSnapshot` validates a stored snapshot whole: an unknown item id, an equipped key naming no sub-slot the crawler has, an item under a sub-slot it does not fit or that the crawler may not wear, a duplicate, or a missing field fails the save, which is then discarded (see CLAUDE.md "Saves"). On restore every slot is rebuilt from the current `ITEM_DEF` keeping only its quantity (`restoredSlot`). A new snapshot field is required, written by `snapPlayer` and checked by `parsePlayerSnapshot`; there is no version and no default for an older save. Add the case to `npm run verify:player-snapshot`.

## Rarity, catalogue, sources, fairy charms and testing

- **Rarity** is one ladder, `Common`, `Uncommon`, `Rare`, `Epic`, `Legendary`, `Divine` (`RARITIES` in `src/core/items/defs/rarity.ts`, with `isRarity`, `rarityRank` and `rarityAtLeast`). A reward chest's `rarity` picks what `rollRewardChest` (`src/loot/rewardChest.ts`) rolls for it at the moment it is earned: coins, health potions and gear from the general roll pool the crawler can wear. Its colour is `rarityColor(theme, rarity, shade?)` in `src/ui/screens/dialogs/canvasChrome.ts`, the one mapping onto `palette.rarity` (`base`, `light`, `deep`, `glow` per rarity); never pick a rarity colour any other way.
- **Reward chests.** Every achievement pays a chest of its rarity, and so do AI gifts, challenge wins, repeat boss kills and some wheel prizes. All of them go through `AchievementAwards` (`src/systems/AchievementAwards.ts`: `unlock`, `advance`, `grantChest`), which rolls the contents with `rollRewardChest` plus the achievement's `fixed` rewards, pays them into the crawler's bag and purse at once, and queues a `RewardPresentation`. The presentation waits behind the HUD's "Rewards waiting" chip (`AchievementUISystem`) and the Reward Chest screen (`src/ui/screens/rewardChest/`) only pictures what was already paid; it never opens on its own and never grants anything. A new item that an achievement hands out is a `fixed` entry on its `ACHIEVEMENT_DEFS` reward.
- **Sets.** `src/gear/sets.ts` holds `GEAR_SETS`, a complete record over `GearSetId`; each set's bonuses switch on at a count of pieces worn on one crawler and are traits (`SetBonusTrait`, which refuses `cursed` and `grantsAbility`). A piece joins a set only through `set` on its def: `setProgress.ts` derives the piece list, pips and completion. Completing any set unlocks `dressed_for_the_occasion` through `GearSystem.onSetCompleted`.
- **The catalogue** — every piece of gear a player can come by lives in `GEAR_CATALOGUE` (`src/gear/catalogue.ts`), spread into `ITEM_DEFS`, with every number its traits read as a named constant there. Worn gear, claws, trinkets and relics have hand-painted icons in `src/sprites/art/itemIcons/gear*Icons.ts` (one module per family: head, torso, limbs and the buckler, claws and relics, trinkets), each a closed id union dispatched through a `Record`; a new piece adds its id to its family's union and a painter. A hand weapon's icon is `heldVisual(id)`. A gear piece's price is `gearPrice(id, multiplier)` in `ITEM_PRICES`: its rarity's `RARITY_BASE_PRICE` times the piece's own worth.
- **Names follow their sub-slot.** A word that names a kind of gear (vest, coat, harness, boots, charm, claws…) belongs to one sub-slot, listed in `ItemNameSubSlotRules` (`src/core/items/defs/itemNameRules.ts`); two pieces share a word only if they fit the same sub-slot and so cannot be worn together, and a name need not use any listed word. `ITEM_DEFS` and `GEAR_CATALOGUE` are built with `defineItemDefs`, so a name holding another sub-slot's word fails to compile with an `__error` naming the item, the name and the sub-slot it borrowed from. Words match whole (lower-cased, split on spaces and hyphens). A new kind of piece adds its word to its sub-slot's list.
- **Sources and pools** — `GEAR_SOURCES` (`src/loot/gearPools.ts`) names where each piece comes from, and every pool is derived from it: `rollGearFromPool(query, rarity, rng, owns)` (the rolled rarity or the nearest one with a piece the party lacks; reroll once on an owned piece, then pay `duplicateCoins`), `rollKillGear` (the per-kill floor pool by floor weights, named `mobDrop` creatures, and a boss's signature pieces plus its boss-pool roll from floor 2), `rollChestGear` (world chests) and `withGearLoot` to add a roll to a `LootDrop`. Kill gear rides the normal loot fall; boss gear goes into the boss chest. A quest pays gear through `grantQuestGear` (`src/loot/questGear.ts`), which returns its `QuestRewardScreen` line. Gear is one per party: always ask `partyOwnsGear`.
- **Fairy immunity.** `fairyImmunities: FairyElement[]` (`'ice' | 'fire'`) on an item def makes its wearer immune to that fairy magic while equipped (`EquipmentManager.hasFairyImmunity`). It is checked at each fairy damage site through `isImmuneToFairyElement` (`src/core/items/equipment/fairyImmunity.ts`), usually via `FairyImmunityFeedback.blocks` (`src/systems/fairyImmunityFeedback.ts`), which also shows "IMMUNE" — never in `Player.applyStatus` or `takeDamage`, since a fireball's burn carries no applier and every non-fairy ice or fire must still land. A new fairy element source must ask it too.
- **Testing.** The `!give <item_id> [quantity]` chat cheat (`ChatKit.giveItem`) puts any item (one by default) in the active crawler's bag, or the wearer's when the def sets `wearer`; non-stackable copies each take a slot.

## Storage mechanics (usually no changes needed)

`Inventory` (`src/core/items/inventory/Inventory.ts`) is a facade over `ItemBag`, `Hotbar` (8 slots), and equipment. The bag is unbounded: it is laid out in pages of `BAG_PAGE_SLOTS`, grows a page when its last empty slot fills and sheds trailing empty pages (`ItemBag.fitPages`), so `addItem` always stores the item and nothing checks for room. Code that writes `bag.slots` directly calls `fitPages` after, or uses `replaceAll` / `placeInFirstEmpty`; the inventory screen shows the bag a page at a time with a pager. `addItem` routes quest items to the reserved quest slot through `replaceQuestSlot`, otherwise stacks hotbar → bag → first empty. The quest slot holds one quest item: granting a different one **evicts** what was there, and the running scene reports it as `questItemEvicted { itemId, crawler }` (`src/systems/questItemEvictions.ts`). A new quest item therefore needs a recovery path, the way Merrit's scythe goes back on its pegs and the blueprints back in Wendell's plan chest the moment no crawler holds them; read held items off the inventories rather than mirroring them in quest state. A quest retiring its item calls `clearQuestItem(id)`, which empties the slot only if it holds that item. `stackable` and `canHotlist` in the item def drive stacking and hotbar placement.

Finish with the `dev-workflow` gates (typecheck, lint, format).
