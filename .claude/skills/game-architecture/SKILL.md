# Game Architecture

Browser dungeon crawler: TypeScript + one HTML5 Canvas, no framework, bundled by esbuild (`scripts/build.js` → `dist/bundle.js`). Optional Express+SQLite backend (`server/`) for auth/progress. The README's "Project Structure" section is accurate — skim it first.

## Core loop

- Entry: `src/game.ts` → creates `InputManager` + `SceneManager`.
- `SceneManager` (`src/core/Scene.ts`) owns the canvas, attaches all DOM listeners once, and runs a fixed-timestep loop: 60 Hz `update()` via accumulator, `render()` once per rAF. `replace(scene)` calls `onExit`/`onEnter`.
- Each rendered frame `SceneManager` first calls `beginRenderFrame()` (`src/core/rendering/renderFrameClock.ts`; `renderFrameNumber()` is what the environment-sheet cache and `RecentSurfaceCache` read to tell "drawn this frame" from "not lately" for eviction over budget; their idle sweeps read `idleFrameNumber()`, which stands still while held; the figure cache and each map's tile chunk cache count their own frames), then `beginFigureFrame()` and `beginEnvironmentArtFrame()`, which drain the paced bake queues. Each cache spends a per-frame time budget, never a count: figure cells `FRAME_BAKE_BUDGET_MS` (4, prewarm's share `PREWARM_BAKE_BUDGET_MS` 3), environment sheets `ENVIRONMENT_PAINT_BUDGET_MS` (8), tile chunks `CHUNK_BAKE_BUDGET_MS` (4, of which ground off screen gets `CHUNK_SPECULATIVE_BUDGET_MS` 1). A heavy arrival drains them behind an `ArrivalLoader` instead. Budgets and byte limits: `docs/asset-management.md`.
- **What stays resident follows the party.** `DungeonScene` owns one `WorldResidency` (`src/systems/WorldResidency.ts`, `residency`) on every floor; resident sets register with it (`EnvironmentSheetResidentSet` for buildings' facades and the floor-wide sheets, `CrowdResidentSet` for a crowd's looks) and it holds, warms and releases their entries by distance from the crawlers and any coming warp landing, every `RESIDENCY_CHECK_INTERVAL_UPDATES` updates and at once (`settleNow`) where the party is set down. Who releases what: the caches' own idle release (sheets, figure rows, tile chunks, interior props; sheets and props age on `idleFrameNumber()`, which `ArrivalLoader` and `BuildingInteriorScene` hold with `holdIdleClock`, so time behind a card or indoors ages nothing); `residency.releaseAll()` wherever a `DungeonScene` gives up its world; a scene's own tile art on its `onExit` (`GameMap.releaseTileArt`, skipped while a building visit holds the floor, `floorArtHeldByBuildingVisit`); and at the stairs `releaseSpritesExcept`, `releaseEnvironmentArt` and `flushFigureFrameCache`. See "Memory follows the party within a floor" in `docs/asset-management.md`.
- Scenes: `DungeonScene` (main orchestrator, ~3k lines), `BuildingInteriorScene`, `GameplayScene` (shared camera/HUD/companion logic), `TitleScene` (`src/scenes/title/`: the title screen and its menu, a layer stack listed in `TITLE_LAYERS`). A `Scene` implements `update()` + `render(ctx)` and takes input through its `ui: UiRoot` (see Input). Localhost review scenes extend `PreviewScene`.

## Systems

~30 plain classes in `src/systems/` implementing `GameSystem` (`src/systems/GameSystem.ts`): optional `update(ctx: SystemContext)` + `dispose()`. `SystemContext` carries per-frame shared state (`human, cat, active, roster, gameMap, bossRoom, ...`), where `roster` is the scene's `MobRoster` — `roster.mobs`, `roster.grid`, and `roster.add(mob)` as the one spawn path.

- Systems are fields on `DungeonScene`, constructed in its constructor with explicit deps (`gameMap`, `bus`, `addMob` callbacks).
- `DungeonScene.updateGameplay()` calls each system's `update(ctx)` in an explicit order; `src/systems/GameLoopPhases.ts` documents the 9 named phases.
- Rendering is layered by `src/systems/RenderPipeline.ts`: world → entities (Y-sorted by `entity.y`) → effects → visibility fog. Being in the roster's spatial grid is what gets a mob rendered (`RenderPipeline` draws from `roster.grid.queryRect`), and `roster.add` puts it there — no extra registration. A dead mob leaves the grid unless it declares `rendersWhenDead`.
- Systems don't play audio directly; they set pending flags (e.g. `explosionSoundPending`) that the scene reads and clears.
- Music is never played, only claimed: systems and scenes call `claimMusic` / `releaseMusic` on the scene's `AudioScope`, and the `MusicDirector` (`src/audio/music/MusicDirector.ts`, `audio.music`, outlives scenes) plays the highest layer's newest claim and falls back on release. Loops and ambient beds also start only through the scope. See `add-sound`.

See the `add-system` skill for the recipe.

`src/economy/` is every price in the game: item base prices (`itemPrices.ts`), shops and their markups (`shops.ts`), stock curves and restock (`stockCurves.ts`, `shopStock.ts`), the pricing engine (`pricing.ts`), and coin fees for services (`servicePrices.ts`). `npm run report:prices` prints the result.

### Scene kits

`src/systems/kits/` groups the systems that make a _place_ rather than a _floor_, so a new environment gets them by construction instead of by hand-wiring:

- `SceneWorld.ts` — `MobRoster` (list + spatial grid + the one `add` path) and the `SceneWorld` record (`gameMap`, `bus`, `audio`, `pm`, `roster`). One world per **map**; one bus per **scene**.
- `CombatKit` — spells, mob AI, attack/death resolution, gore, floating numbers, seismic stomp, regen, death screen.
- `DestructionKit` — smashable props, floor loot, dynamite.
- `MenusKit` — inventory screen, pause screen, award stack, toasts, potions, skill books; `menus.surfaces(...)` lists the surfaces it mounts.
- `ChatKit` — chat box plus the universal cheat table.
- `CutsceneKit` — the `CutsceneDirector` (`src/systems/cutscene/`) and the surface that hands it the party: walk-ups, talks, Caroline's messages, Dave teleporting out, camera pans and shakes, sounds and the scene's own world actions, played as typed `CutsceneStep` lists. Its `isActive` is the one answer to "does a script own the party". See `add-system`.
  - Step kinds beyond walking and talking: `panCamera` / `holdCamera` / `returnCamera` (the director's `cameraFocus` sits in `DungeonScene.camera()` ahead of the AI spotlight and behind the tutorial and spider-quest overrides), `shake` (a `ShakeProfileId` from `cutsceneShake.ts`, summed into the camera offset through `cameraShake`), `sound` (a cue's takes, optionally positional) and `run`, whose `action` is the playing scene's own world-action union. The dungeon's is `DungeonWorldAction` (`src/scenes/dungeonWorldActions.ts`): a payload table plus a `DungeonWorldActionHost` with one handler per kind, so a new kind fails to compile until the scene handles it (today `gatherParty`, which sets the whole party down inside a tile rect and stands the downed back up). Every step advances on world ticks, so a script holds under the pause menu.
- `ScriptedDeathSystem` (`src/systems/scriptedDeath/`, `DungeonScene.scriptedDeaths`) — deaths a script shows rather than a blow deals. `ScriptedDeathKind` (`scriptedDeathKinds.ts`, a leaf module `Player`'s `DamageSource` can name) keys `SCRIPTED_DEATHS: Record<ScriptedDeathKind, ScriptedDeathDef>` (`scriptedDeaths.ts`): the animation painter and frame count, the decal left behind, the delay before the death screen, the `DeathCause` and the sound cue. `play(kind, victim, at)` plays it through a cutscene (input held, victim hidden once taken, protected from other harm), then kills through `Player.dieScripted`, which no dodge, ward or 9 Lives stops; the ordinary death check raises the death screen and the run goes back to its last save. A new scripted death is a new kind and a new table entry.
- `MashInteraction` (`src/systems/MashInteraction.ts`) — a thing a crawler works by pressing interact again and again (a valve wheel, a crank). Unlike a `WorkChannel` nothing runs on its own: walking off leaves the progress where it was. A `MashInteractionDef` supplies the prompt deed, press count, human rows, bar style and reach; the owner supplies what a press sounds like and what finishing changes.
- `drawObjectiveMark` (`src/sprites/objectiveMark.ts`) — the quest beacon and bouncing `!` over a world object the party has to deal with (a pedestal prize, a machine to shut down). It marks a thing, not a person; an NPC's marker comes from its own marker state.
- Dungeon water (`src/map/dungeonWater.ts`) — standing water on dungeon floor, the river's wading model reused. `GameMap.floodWater` / `drainWater` / `advanceWaterDrains` change and repaint it at run time; the recipe is in `add-level` ("Dungeon water").
- `hotbarActions.ts` — what pressing slots 1–8 does, for every scene that has them.

Kit fields stay concrete types: `update` signatures are not uniform, so a `GameSystem[]` loop could only be reached through casts. `npm run verify:kits` gates the spine.

`DestructionKit` also owns `GroundPickupSystem` (`src/systems/GroundPickupSystem.ts`): visible world pickups such as a dead cow's burgers, collected all at once by one Space press, carried through door visits and death rewinds.

**Floor-3 kits.** Two more kits hang off `DungeonScene` as one field each, with one-line call sites:

- `GatheringKit` (`src/systems/briarHollow/GatheringKit.ts`) — harvesting any tree or boulder, thralls, the resource HUD and the village's node regrowth. Built on every overworld floor, village or not. It owns exactly one link in the Space chain, after citizen and village talk.
- `BriarHollowKit` (`src/systems/briarHollow/BriarHollowKit.ts`) — Briar Hollow: villagers, the herd, services (`VillageServices`), construction and the siege engines (`ConstructionKit`, held as `defences`), soldiers, the Plea (`VillageQuestSystem`) and its assault, Fenna's side quest The Borrowed Blueprints (`BlueprintsQuestSystem`, whose parts live in `src/systems/briarHollow/blueprints/`; see `docs/town.md`), and Wendell's construction contracts' village side (`ConstructionContractSystem`, `src/systems/constructionContracts/`; see `docs/town.md`). Built only when `gameMap.briarHollow` is non-null (every floor-3 world). It is rebuilt on every door visit, so its systems keep nothing durable themselves: they read and write the `BriarHollowState` threaded by reference through both scenes (`src/core/quests/briarHollowState.ts`), the same way `TownMemory` is. Its render hooks (`renderGround`, `renderEntities` merged into the Y-sort, `renderAbove`, `renderHud`), `topBandEntries()`, `surfaces(camera)`, `tryInteract`, quest markers and tracker entries follow the boss-room dressing slots below.

`CloggedBathroomSystem` (`src/systems/cloggedBathroom/`, `DungeonScene.cloggedBathroom`) runs floor 2's clogged bathrooms: the invulnerable `BathroomGoblin` queue and plumber in every copy, the floor's one pipe board (generated on first open, behind its explainer) and its surfaces, the stall visit and its `refreshed` status, and the "The Clogged Bathroom" mini quest. Its link in the interact chain, its render slots (`renderGround`, `sortedFixtures`, `renderAbove`, the `isCrawlerHidden` render predicate), `questMarkers` and `trackerEntries()` follow the boss-room dressing slots below. The map half is in `add-level`.

`StealthKeySnatchSystem` (`src/systems/stealthKeySnatch/`, `DungeonScene.stealthKeySnatch`) owns floor 2's stealth gate: the gate guard (a `PrisonGoblin` in the `gateGuard` role), the PRISON sign, the mini quest "The Stealth Key Snatch" and its phase (`StealthKeySnatchPhase`: `unmet` → `briefed` → `keyHeld` → `opened`, following `quest_prison_key` in the inventories), and `gameMap.setStealthGate`. The prison door refuses an unbriefed party (`prisonDoorRefusal`, read by `DungeonScene.sealedBuildingMessage`). The quest is checkpointed and saved as `StealthKeySnatchCheckpoint` (`WorldCheckpoint.stealthKeySnatch`, `PersistedWorldState.stealthKeySnatch`). The system is the `StealthKeySnatchVisit` the prison reads through its floor context; `detachedPrisonVisit` stands in for a dev route or harness with no floor outside.

The prison interior (`goblin_prison` variant, map half in `add-level`) runs two systems in `BuildingInteriorScene`:

- `GoblinPrisonSystem` — patrols, lights, suspicion, capture (freeze, fade, both crawlers thrown in the first holding cell, every loop reset; the key and phase are kept) and the breakable `PrisonCellDoor`s. Guards are invulnerable `PrisonGoblin`s; `PrisonerGoblin`s fill the cells. Drawn is caught: one light shape per frame is what the darkness is cut with and what detection tests.
- `PrisonKeySystem` — the key on its pedestal (there exactly when no crawler holds it and the gate is still shut; never stored), guidance and the first-visit explainer. Recall and travel are refused indoors (`refuseAnchorIndoors`), so the only way out is the exit tiles.

Pure modules they share with the solver: `detection.ts` (`castCone`, `castDisc`, `lightSeesBody`), `prisonPatrols.ts` (`prisonStateAt`, a pure function of the frame), `prisonNoise.ts` (`respondToNoise`: alarm when seen, investigate when only heard), `prisonTuning.ts` (`PRISON_TUNING` per difficulty). Art and sound: `prisonGround.ts`, `prisonLighting.ts`, `prisonSoundCues.ts` (`PRISON_CUES`, preloaded through the `stealthKeySnatch` sfx group). Neither companion is admitted: they wait on the gate room's `waitingTiles` (`seatCompanionsWaitingOutsidePrison`). Gates: `verify:stealth-key-snatch-play`, `verify:prison-capture`, `verify:prison-stealth`.

`EmoteEffectSystem` (`src/systems/EmoteEffectSystem.ts`) draws floating emotes (a petted cow's hearts) and is built to take other emote kinds.

### Safe rooms and Dave

`SafeRoomSystem` knows a map's safe rooms (`SafeRoomId`, `src/map/safeRoomId.ts`) and where Dave stands and wanders in each (`guidePlacement`). `DaveGuideSystem` (`src/systems/DaveGuideSystem.ts`) is the one Dave in a scene: he teleports into whichever safe room the party last walked into (`onSafeRoomEntered`, after `DAVE_ARRIVAL_DELAY_FRAMES`), stays there until they enter another, wears his `!` while he owes tactics for the current objective, and is drawn by `drawDaveSprite` (`src/sprites/daveSprite.ts`). Where he is outlives a scene in `DaveWhereabouts`, threaded between the dungeon and a building's safe room by `InteriorPartyRun`, so a reload finds him in the party's room. `DungeonScene` and `BuildingInteriorScene` (the Sleeping Cat Inn) each build one; what he says is the Story section's.

### The town

The floor-3 town's systems, and where each rule lives. The durable description is `docs/town.md`.

- **Street:** `TownLifeSystem` runs the crowd, rolled from the world seed; its looks are pinned in the figure cache by distance from the party through a `CrowdResidentSet` the scene registers with its `WorldResidency`. `TownPropSystem` places the plaza fixtures, `TownDecorSystem` the yard and doorstep dressing, and `MarketSystem` the stalls. All three refuse `doorwayKeepClearTiles` (`src/systems/doorwayKeepClear.ts`), because a connectivity check cannot see a door being sealed. Citizens dispatch by species through `src/creatures/citizenFigure.ts`.
- **Interiors:** layouts are data in `src/map/town/interiors/`, with props from `TOWN_INTERIOR_PROPS`. Buildings are keyed by `BuildingId` (`src/map/buildingIds.ts`); the sign's text is `buildingDisplayName(id)`, for display only.
  - `InteriorOccupantSystem` seats the room's people.
  - `InteriorPropInteractionSystem` runs examine, search and use; `InteriorReadableSystem` runs paged documents.
  - `TownInteriorPropDestructionSystem` breaks placed props, and `InteriorBreakReactions` captions the reactions.
  - `townInteriorPropFigures.ts` splits walkable ground props from Y-sorted ones.
  - `src/scenes/interiorCamera.ts` frames the room clear of the HUD: `interiorHudOccluders` (`src/scenes/interiorHud.ts`) turns the shared HUD layout (`liveHudLayout`) into occluders for `hudClearView`.
- **Memory:** `TownMemory` (`src/core/state/TownMemory.ts`) is threaded by reference through both scenes, like `BriarHollowState`: resident talks, cleared rooms and camps, and props that have paid out.
- **Talk:** `src/dialog/walkAway.ts` is the one walk-away rule. `src/systems/safeRoomSpeaker.ts` decides whether a press in the safe room is for the Bopca or Dave.
- **Arrival:** `findPartyArrivalTiles` (`src/map/findWalkableTile.ts`) sets the party down on every arrival. Every gameplay scene, on every floor, arrives behind an `ArrivalLoader` (`src/scenes/ArrivalLoader.ts`, abstract on `GameplayScene`); `src/scenes/floorArrivalLoad.ts` builds its tasks, run by `LoadRunner` (`src/core/perf/LoadRunner.ts`). See `add-level`. Behind the loader a `DungeonScene` floor opens on the "find the stairwell" banner (`DungeonIntroSystem`, itself a surface): until it is mostly faded (`arrivalSettled`; skipped by `skipIntro`, the tutorial and every door, respawn or harness that passes it) it is a `modal` that halts the world, so the player cannot act and every arrival trigger (Dave, the story's opening, the arrival save, the collapse clock, spawns and aggro) waits for the first live world frame. A new arrival trigger belongs in that frame, never ahead of the scene's halt.

### The Cloak & Dagger casino

`CloakAndDaggerSystem` owns the club's stations; its "Play" prompt at the casino opens one game picker (Slots, Texas Hold'em, Blackjack, Wheel of Fortune). Blackjack (`ClubCasinoSystem`) and poker (`ClubPokerSystem`) are built by the club itself. The slots and the wheel are `CasinoGameHost`s (`src/systems/casino/CasinoGameHost.ts`), held as `CasinoGameHosts { slots, wheel }`: a host opens on a `CasinoSeat`, lists its surfaces (mounted with the club's), ticks every club frame and keeps the casino music on while open. `ClubSlotsSystem` is built by the club over the canvas-free engine in `src/systems/casino/slots/` (`SlotMachine`); `ClubWheelSystem` is built by `BuildingInteriorScene` and seated with `installCasinoGame('wheel', …)`, because it needs the scene's save, wipe and attack-cow grant. A game not yet installed is an `idleCasinoGameHost()`. The wheel's rules (board, rigged weights, red-wedge effects, prize payouts) are canvas-free in `src/systems/casino/wheel/`; its screens in `src/ui/casino/wheel/`, the slots' in `src/ui/casino/slots/`. See `docs/town.md`.

### Buildings under a dungeon floor

`DungeonScene` builds a `BuildingSystem` on any floor whose map has `buildingEntries` (floor 2's prison door is one), not only the overworld. `floorRegeneratesAroundBuildings` decides what a door does with the floor:

- **Overworld:** regenerated around the party on the way out.
- **Any other floor:** held aside. `holdFloorForInterior` writes a save at the door when one is allowed (no fight, boss or revive pending), then returns a `DungeonInteriorReturn` (`src/scenes/dungeonInteriorReturn.ts`, memory only): the live crawlers and population (corpses included, less the mobs systems stand up themselves), a `WorldCheckpoint`, the collapse clock, the return tile and the last save. The scene rebuilt on the way out takes it as `interiorReturn` and calls `applyWorldCheckpoint(world, frames, 'keep')` instead of spawning a floor; `withVisitOutcome` folds back the quest state the interior changed.
- `applyWorldCheckpoint` is shared with the death rewind (`'rewind'`): both run `restoreFloorCheckpoint` (the floor's systems); only a death also runs `restoreRunProgress` (tallies, companions, threaded objects), because the party kept spending and earning indoors.
- The interior reads its floor through `InteriorFloorContext` (`src/scenes/interiorFloorContext.ts`; `TOWN_INTERIOR_FLOOR` for the town): floor number, ground sheets and sprite groups (built by `interiorArt`, which adds the floor's indoor-only `LevelDef.interiorSpriteGroups`), sight radius, whether it owns the music, `heldLevelTimerFrames` (the collapse clock shown paused; nothing indoors ticks it), and the optional `variant` and `stealthKeySnatch` visit for the prison.
- A defeat indoors rebuilds the held floor first and then calls `respawnAfterDeath()`, so it rewinds exactly like a death outside.

Gate: `npm run verify:dungeon-interior-return` (same creatures and systems back, party at the door, clock held then running, door save resumes in front of the door).

### Boss-room dressing

Each boss room's props, slow ground, hazards and interactables belong to a dressing in `src/systems/bossRooms/`, separate from the boss and from the fight owner (`BossRoomSystem`, `SpiderQuestSystem`): `TrashGremlinRoomSystem`, `GymRoomSystem` (in `src/systems/`), `PowerLabRoomSystem`, `FloodedPumpRoomSystem` and `SpiderLabDressing` (owned by `SpiderQuestSystem.labDressing`).

- **Contract** — `BossRoomDressing.ts`: `update`, `renderGround`, `renderEntities`, `renderAbove`, `resetForCheckpoint`, `tryInteract`, the `BossFightHooks` (`onSeal`, `onBossDefeated`, `onFightAborted`), `GroundHazardSource.getHazardEscapeVector`, `sealRule` (`BossRoomSealRule`: `on_entry`, where `BossRoomSystem` locks the room as a crawler walks in, or `held_by_room`, where it locks exactly while the room says it is sealed), and `CheckpointedDressing` (`captureCheckpoint`/`restoreCheckpoint`, typed per room). Extend `InertBossRoomDressing` and override only the hooks the room uses.
- **Aggregator** — `BossRoomDressings` holds every room as a named field (not a list, so each checkpoint keeps its type). `buildGauntletRoomDressings` finds gauntlet rooms by boss type, never by index into `gameMap.bossRooms`. It is `BossRoomSystem.fightListener` and one hazard source for companions and mob tactics.
- **Death path** — the scene calls `resetForCheckpoint` then `restoreCheckpoint` (from `WorldCheckpoint.bossRoomDressing`); the restore has the last word. A death is never an `onFightAborted`, which means only "fight ended, party still playing, boss healed".
- **Idempotent defeat** — `replayDefeats` re-sends `onBossDefeated` after every build and load for bosses already dead, so the hook must tolerate repeats.
- **Render slots** (`RenderPipeline`) — `renderGround` right after the map's own ground (tiles, gore, trees, river) and before every floor hazard and warning, `bossRoom.renderObjects` (the Kraken's slam shadows) included, so a warning always shows on top of a room's ground props; `renderEntities` merged into the Y-sorted pass as prop entries; `renderAbove` in the effects pass, over every body.
- **Ground and sight** — slow ground is a tile type in `src/map/tileSpeed.ts`, applied by `footingSpeedFactor` in `GameLoopPhases.applyMovement`. Low props are in `SIGHT_TRANSPARENT_TILE_TYPES` (`walkability.ts`): `GameMap.hasLineOfSight` sees over them, so steering straight at a point must ask `GameMap.hasWalkableLine` instead. Room hazards that kill carry their own `DamageSource` (`trashAvalanche`).
- **Layout** — `bossRoomLayout.ts`: doorway-relative templates (`rotateTemplate`, `stampProps`) and the keep-clear sets `approachLaneTiles` / `spawnClearTiles`.
- **The flooded pump room** — `FloodedPumpRoomSystem` runs the Kraken's floor-1 room from one state union (`FloodedPumpRoomState`: `approach`, `intro_cutscene`, `flooded`, `draining`, `drained`, `defeated`; every change through its `transition`), laid out once per map by `planFloodedPumpRoom` (`floodedPumpRoomLayout.ts`, cached because it costs about a third of a second): a lattice of small rafts, a landing raft by the door and a raft moored beside each wall pump, every float's shark loop solved there. Crossing the corridor's trigger line plays the intro through the scene's cutscene director (its beats come back as the `floodedPumpRoom` world action); the one shark moves by `stepShark` in `floodedPumpRoom/sharkModel.ts` through water-only paths (`floodedPumpRoom/waterMap.ts`), patrolling the loop of whichever float the active crawler stands on; it is the model `verify:kraken-flood` proves, and takes only the active crawler through `ScriptedDeathSystem`; raft and pump tentacles are `KrakenTentacle`s in the `raft`/`pump` roles; each pump is a `MashInteraction` hauled only from its own raft. It holds its own seal (`held_by_room`), puts the companion and hire on the leader's trail while flooded (`partyWalksTrail`), tells the Kraken when it is drained (`KrakenRoomControl`), and re-applies its water and barrel blocks on every restore, since map water is not part of a saved world. A barrel stands on every tile of every doorway but the entrance (`layout.exits`) until the Kraken dies, blocked like the corridor's barrels, and bursts as her room's seal releases. Each pump shut off is the run's save (`FloodedPumpRoomStage.savePumpProgress`, the one save taken while a boss room is sealed), so a death or a reload comes back to the landing raft with the pumps already done. The scene advances `GameMap.advanceWaterDrains` on world ticks.
- **Gates** — `npm run gates:boss-rooms` (`scripts/gates-boss-rooms.ts`, per-room modules in `scripts/bossRooms/`, shared `harness.ts`) checks the tile contract, sheets, and every seed's approach/spawn/reachability, then each room's own gates; `--room=<name>` narrows it and `--fault=<name>` must turn it red. `npm run render:boss-rooms` bakes review images.

### Cross-cutting getters

Two seams cut across the quest systems instead of living in one owner, because
some questlines keep a `QuestManager` privately and others have none at all —
centralising the state would mean rewriting every one of them.

- `questMarkers` — minimap pips, gathered by `DungeonScene.collectQuestMarkers()`.
- `trackerEntries()` — Quest Journal rows, the `TrackerSource` interface in
  `src/systems/questTracker.ts`, gathered by `DungeonScene.collectTrackerEntries()`.

Both are rebuilt from the system's own phase machine every frame and stored
nowhere, so neither can go stale. See `add-quest`.

### Saving and wiping

- **One validator, data only.** `parseGameProgress` (`src/core/save/saveFormat.ts`) is the check for every stored save, in the browser and in the Express server's progress route alike, so the two never disagree. It and every parser it calls reach only data shapes: id lists and plain records (`achievementSave.ts`, `playerSnapshotFormat.ts`, `PersistedWorldState.ts`, `storyBeatIds.ts`, `villagerIds.ts`, `residentIds.ts`, …). Where a parser needs ids whose owner paints, speaks or plays, the ids live in a leaf module the owner imports; the game side builds on what the parser accepts (`AchievementManager.parse`, `persistedWorldCapture.ts`). `npm run check:server-imports` (in `npm run check`) bundles the server and fails if it loads art, audio, dialog, UI, scenes or DOM code.
- **Storage keys.** Everything the page stores lives under `kcw.*` keys (`kcw.progress`, `kcw.settings`, `kcw.wipeOwed`, `kcw.aiFloorLedgers`, `kcw.aiForgottenNotice`), and the service worker names its caches with a `kcw-` prefix and deletes only its own: the game shares its origin with everything else on `ryanscarbel.com`, and must never read or clear another page's data.
- **One door to the save slot.** `ProgressPersistence` (`src/core/save/progressPersistence.ts`) carries every save and the wipe for the page. `PAGE_SAVE_LATCH` is the page-lifetime switch every real write path checks (`writeLocalProgress`, `AuthClient.saveProgress`, the persistence); once engaged it never disengages, so nothing written on the way out of a wiped run can bring it back. A gate builds its own with `createSaveLatch`.
- **Wipe.** `ProgressPersistence.wipe()` engages the latch, records an owed wipe in `localStorage` (`LOCAL_WIPE_MARKER`, `src/core/save/wipeMarker.ts`), drains writes in flight, deletes with backoff until it lands, then clears the marker. A wipe still owed when the tab closed is finished by `bootProgress` before anything loads, behind `WipeHoldScene`, and the page then reloads (`reloadPage`). Scenes reach it through the `progressWipe` option (`ProgressWipe`, `src/ui/screens/dialogs/wipeHold.ts`). **Reset Game** and the wheel's Nothing are the same path: the wipe behind a `WipeHold`, then a reload, so no in-memory state outlives it.
- **Party-run state outside the floor.** `WheelLedger` (`src/core/save/WheelLedger.ts`: prizes won, a pending outcome, owed free spin, freeze and quest free spins) and `AttackCowState` (`src/core/state/AttackCowState.ts`) are threaded by reference through both scenes (indoors via `InteriorPartyRun`, `src/scenes/interiorPartyRun.ts`) and saved as top-level `GameProgress` fields (`wheelPrizesWon`, `pendingWheelOutcome`, `wheelFreeSpinBet`, `wheelOwedFreeze`, `wheelQuestFreeSpins`, `attackCowOwned`, `attackCowHp`, `attackCowResting`), so they survive floor changes. The pet names (`PetNameBook`, `src/core/party/petNames.ts`, saved as `petNames`) and the story's seen beats and briefed objectives (`storyBeatsSeen`, `objectivesBriefed`, written at once outside the checkpoint by `persistStoryBeatsSeen`) are run state of the same kind, and none of them is rewound by a death. A wheel spin is committed to the save before the wheel turns; a pending outcome left by a closed tab is paid on the next load. `src/core/save/doubleDamageSave.ts` (`doubleDamageRemaining`) carries the incurable double damage across saves, since snapshots rebuilt from a save drop their statuses.

## Entity hierarchy

`Player` (`src/Player.ts`, abstract: position, HP, stats, status effects, walk animation) → `HumanPlayer`, `CatPlayer`, and `Mob` (`src/creatures/Mob.ts`, abstract: aggro, A* pathfinding, LOS, health bar, loot). All enemies extend `Mob`. See the `add-creature` skill.

### Who the player is

The human crawler is the player's own: they type a name and choose a body (`CrawlerBody`, male or female) and a complexion (`Complexion`) on the title's character creation screen. The cat is always Belle, a fixed registry character (`PLAYER_CHARACTERS`, `src/characters/characters.ts`). The human has no character id and no entry in `CHARACTERS`.

- **Where it lives.** `src/characters/playerIdentity.ts` holds the run's `PlayerIdentity` (`name`, a branded `PlayerName` only `parsePlayerName` in `src/core/naming/` makes; `body`; `complexion`) as module state, for the same reason `humanSprite.ts` holds one resident look: there is one player, and every picture and line of them must agree. `playerIdentity.ts` holds data only; `humanSprite.ts` follows it (`followPlayerIdentity`) and calls `setHumanLook(HUMAN_CRAWLER_LOOKS[lookIdOf(identity)])` (`src/characters/humanCrawlerLooks.ts`, a `Record<HumanCrawlerLookId, HumanLook>`) on every new identity, so only the chosen look is ever resident and the name can be read without loading art. The creation choices (`CrawlerBody`, `Complexion`, `lookIdOf`) are `src/characters/crawlerChoices.ts`. Pronouns come from `crawlerPronouns(kind)` (`CRAWLER_PRONOUNS`, `src/characters/crawlerPronouns.ts`) and the human's hurt, knocked-out and revived sounds from `humanVocalSounds()` (`HUMAN_VOCAL_SOUNDS`), both following the body.
- **Who sets it.** Only these: the creation screen's confirm (`TitleScene`); `sceneSetupFromSave` (`src/scenes/resumeFromSave.ts`) and the boot path in `src/game.ts` that reads a save before the title paints its heroes; dev boot (`src/dev/devBoot.ts`, every route but `?title` without `&save`, which leaves it unset so creation can be tested); and every harness under `scripts/` that builds a scene or reads a crawler name, through `useDevPlayerIdentity()` (`src/dev/devPlayerIdentity.ts`, `DEV_PLAYER_IDENTITY`) called right after its imports. The identity is a run field of the save (`playerIdentity`); a save without a valid one is discarded.
- **The throwing read.** `playerIdentity()` throws when no identity is set. That is the rule's enforcement: a module that reads the name when it loads crashes every boot and gate on its first run, so read the name when the text is built (a function, a `.fn` line, a getter), never into a module constant. A harness that throws here is missing `useDevPlayerIdentity()`; never add a silent default inside the game. Only the title screen may ask `maybePlayerIdentity()`, because it runs before a fresh player has a name.
- **`crawlerName`, `crawlerDisplayName` and `crawlerAIName`.** `crawlerName(kind)` is the bare name. Text shown on screen takes `crawlerDisplayName(kind)`, the name wrapped in bidi isolates (`isolateForDisplay`, `src/core/text/isolateName.ts`) so a right-to-left name cannot reorder the line around it; it is never stored or sent to the AI. Text for the AI takes `crawlerAIName(kind)` ("the human crawler" for the human): the typed name reaches the AI server only as the session context's `humanCrawler.name`, which the server fences as untrusted player text. A quest or item whose screen name carries the player's name gives the AI its own (`TrackerEntry.aiName`, `ItemDef.aiName`, read through `readActiveQuests` and `itemAIName`); `verify:ai-context` checks a hostile name appears nowhere else. The human's speaker is `human_crawler`, whose `name` resolves when the line is shown. Nothing maps a name back to a crawler: code keys crawlers by `CrawlerKind`, because a player may name themselves "Belle".

**Damage and HP bands.** A status id is a `StatusId` (`STATUS_IDS`, `src/core/combat/StatusEffect.ts`); each declares its rules in one `STATUS_DEFS` entry, including a multiplier on the damage its carrier takes (`incomingDamageScale`), applied once per blow from any source (`Player.takeDamage` for crawlers, `Mob`'s own door for mobs). A status that `incapacitates` (stun, frozen), or a damage-over-time status whose bite seizes (`seizeTicks`, electrified; `seizureRemainingFraction`), makes `Player.canAct` false: a crawler can then neither walk, attack, cast nor use an item, and `MobUpdateLoop` skips a mob's AI while it keeps its target. `takeDamage` takes `DamageOptions` (`floorHp` stops a blow at a minimum HP). `Player.hp` is an accessor: every write on a crawler checks the bands in `CRAWLER_HP_THRESHOLDS` (`src/core/combat/hpThresholds.ts`), each firing once on entry and re-arming above its line; both gameplay scenes drain the crossings with `drainHpThresholdCrossings`, which runs each band's `onEnter` (`low_health` emits `healthLow`). A save restore writes HP through `restoreHp`, which reacts to nothing.

`src/shelf/` holds finished painted characters with no role yet, one folder each, with their gates and render harnesses in `scripts/`. Nothing in the game imports it; its `README.md` lists the characters and the rules.

**Crawler progress.** Combat skills live in `SkillManager` and spells in `AbilityManager`. A skill's `progression` is `standard` (five quick levels) or `proficiency` (`src/core/skills/proficiency.ts`: fifty levels on one effect curve, `proficiencyEffect`, each boosting every hit that carries one of its `PROFICIENCY_SKILL_TAGS`). Every hit a crawler deals carries `DamageTags` (`src/core/combat/damageTags.ts`: its weapon's family, `magic`, `fire`, `explosion`; a status bite takes its tags from its `damageOverTime` def) and passes through `outgoingHitDamageOn` (`src/core/combat/outgoingHit.ts`), the one place skills join a hit and count it as a use. The six stats (`ALL_STATS`, `STAT_GAIN_PER_POINT`, `DELIVERY_STAT` in `src/core/party/stats.ts`) are shared by both crawlers; each delivery's formula in `crawlerFormulas.ts` folds its stat into the blow, and `computeDodgeChance` (`src/core/combat/dodge.ts`) turns evasiveness into dodge against a per-crawler soft limit. A spell from a mob is magic (`Mob.dealSpellDamage`), turned aside by magic-resistant gear by a share that grows with the wearer's Magic (`magicResistedShare`); the rules are in `docs/difficulty-fairness-rules.md`. Skill books drop from typed weighted pools (`SKILL_BOOK_POOLS`, `src/loot/skillBookPools.ts`) at the one per-kill chance in `skillBookDrop.ts`. The craft skills (Resourcing, Construction) are per crawler: `Player.craftSkills` (`src/core/labour/CraftSkills.ts`), saved in `PlayerSnapshot`; `teachBoth` teaches both crawlers at once, and every perk reads the acting crawler's own level. Tool tiers are shared: `PartyTools` (`src/core/items/gathering/PartyTools.ts`) swaps both crawlers' tool items in place, and it lives with the explainer flags in `partyCrafts` (`GameProgress.crafts`). `src/core/items/gathering/partyResources.ts` counts and spends a resource across both inventories.

### Companions and hirelings

Deinonychus (`DeinonychusSystem`) and The Barracks Mercenaries' hirelings (`MercenarySystem`) are `Mob`s on the party's side, handed to hostiles through `ctx.extraTargets` and crediting their kills to their owner. A hireling is a shell (`Mercenary`) plus a kit (`src/creatures/mercenaries/`), drawn through `MERCENARY_ART` and voiced through `MERCENARY_VOICES`; its shots fly in `RockThrowSystem` and `HirelingShotSystem`. Both companions follow the party everywhere, including indoors: `BuildingInteriorScene` owns its own `DeinonychusSystem` and `MercenarySystem` instances the same way `DungeonScene` does. No door opens while the crawler not being driven is knocked out (`downedPartnerEntryRefusal` in `BuildingSystem.ts`, read by `DungeonScene.sealedBuildingMessage`), so a crawler is never left bleeding out outside; one can still go down indoors. The human's attack cow (`AttackCowSystem`, `src/creatures/AttackCow.ts`, a wheel prize) is a third: once owned she is always out beside the human in both scenes, goes down for a revive rather than dying, rests until the next floor if left, and taunts nearby hostiles onto herself through `Mob.tauntedBy`. A door dismisses whichever companions are out and the scene on the far side rebuilds them fresh — a hire from the roster's saved HP, Deinonychus via `deinonychusWasOut` into `DeinonychusSystem.carryIn`. `src/systems/companionCarry.ts` is narrower: it moves companions that are already out between rosters of the same building, on a tower's `changeFloor` and when a script resets the party to its marks, beside the crawler they follow. See the `add-creature` skill.

### Held equipment and weapons

Weapons are equipment, not a private field on the player.

- **Sections.** `EquipSlot` puts what a crawler fights with in `Weapon` (the human's `Main`, `Off`, `Relic`; the cat's `Claws`, `Relic`) beside the worn sections; `EQUIP_SUBSLOTS` is per crawler, and `MAIN_HAND_KEY` (`src/core/items/defs/ItemDefs.ts`) names the human's main hand. Gear mechanics are traits (`src/gear/traits.ts`, run through `src/gear/gearHooks.ts` and `GearSystem`), never id checks. `EquipmentManager.canEquip` reads the item's own `wearer`. A weapon is an item with `type: 'weapon'` and a `weapon` stat block (`src/core/items/equipment/weapons.ts`: each with a required `family: WeaponFamily`; `MeleeWeaponStats` with `damageMultiplier`, `reachTiles`, `heldVisual` and an optional `onStrike` proc id, or `SlingWeaponStats`; the cat's claws are `ClawWeaponStats`, read through `wornClaws`); `weaponStatsOf(id)` reads a hand weapon's block. How an item looks in the hand is the `add-gear` skill.
- **Drawn or stowed.** The weapon in his main hand (`HumanPlayer.mainHandWeaponId`, equipped in `MAIN_HAND_KEY`, `Weapon:Main`) is the drawn one (`drawnWeapon`, `drawnMeleeWeapon`, `hasSlingDrawn`); a weapon on his hotbar but not in his hand rides stowed on his body. `drawWeapon(id)` equips it into the main hand, `stowWeapon()` unequips it, and `toggleWeaponDrawn(id)` is the hotbar press: `hotbarActions.ts` toggles any slot whose `weaponStatsOf` is non-null; its draw or stow sound plays off `equipmentChanged`. Whatever path changes the main hand plays the motion set's draw/stow rows (`HumanAnimator.beginHolster`), so the drawn state is saved as the equipment itself.
- **One generic strike, procs for specials.** `CombatSystem.resolvePlayerAttacks` routes any drawn melee weapon through `strikeWithWeapon` (the weapon's multiplier and reach, `cutWithWeapon` per mob) on the blow's peak tick. A weapon's special is a `WeaponProc` named by its `onStrike` id and looked up in `CombatContext.weaponProcs`, which `CombatKit` fills (`{ stormcallerStorm: this.stormcaller }`). `StormcallerStrikeSystem` is that proc for the Stormcaller: its lightning wave and chain lightning resolve in the same phase as every other blow, each enemy struck at most once per swing. A second sword needs no new system; a new special is a new proc registered in `CombatKit`. A swing with no proc emits `weaponSwing` for its sound; a proc voices its own. The cat's Kaleidoscope Specs live in `src/abilities/kaleidoscopeSpecs.ts`.
- **Equipment changes are events.** `EquipmentManager.onChange` reports every equip, unequip and restore to its listeners; each crawler subscribes and re-dresses in `onEquipmentChanged` (nothing polls equipment per draw). Scenes forward both crawlers' changes onto their bus as `equipmentChanged` through `forwardEquipmentChanges` (`src/systems/equipmentChangeEvents.ts`), wired on entry and taken down on exit. Gear sound cues are in `src/audio/gearSoundCues.ts`; weapon sounds by family in `src/audio/weaponSoundCues.ts`.

### The human's animation

`HumanPlayer` never chooses a row itself; four modules do, and systems never draw him.

- **`HumanAnimator`** (`src/sprites/humanAnimator.ts`) owns which row he is drawn in and how far through it. `HumanPlayer` feeds it once a tick — ground actually covered (measured from position, not `isMoving`), facing, knockout, the strike and Seismic Stomp timers — and `spriteSelection()` returns the row, frame and mirroring `drawSelf` paints. It is tick-driven and seeded, so the art gates replay it exactly. It owns:
  - **Row choice from metadata**, never names: the view comes from his `FacingState` (`src/sprites/facingView.ts`: eight 45° sectors, five views, a hysteresis margin), resolved through `humanRowView` (`src/sprites/humanSprite.ts`, whose `HUMAN_VIEW_FALLBACK` draws a view he has no rows for in a neighbouring one); a system picks a view-keyed row with `HumanPlayer.rowFacing`, a strike family is "the strikes in this view", chosen by target (low, tall, downed, far) and combo slot within `COMBO_WINDOW_TICKS`.
  - **The gait**: walk or run by smoothed measured speed, phase advanced by radians per pixel covered, starts and stops cut only where the legs already agree (a stride settles to the frame its stop begins from).
  - **Moving strikes**: on the move it never throws a standing blow; it picks the travelling version whose legs begin nearest the stride on screen, and a Seismic Stomp becomes a hop.
  - **Latched facing**: a blow or Seismic Stomp latches its facing and row for the whole swing; `latchedFacing` feeds `HumanPlayer.strikeFacingX/Y`, and the hit is resolved along it, so the damage goes where the drawn fist goes however the stick is steered mid-swing.
  - **Standing**: the guard held after any blow given or taken, its drop to the idle, fidgets after 6–12 s of quiet (suppressed after damage), the level-up gestures.
  - **Scripted rows**: `playAction` / `playReaction` / `stopAction` / `stopReaction` (exposed on `HumanPlayer`), with `loop`, `holdLastFrame`, `faceX/Y`, `cancelOnMove`, `progress`, `onFrame` (callbacks on the tick a frame is first drawn — pass the row's `eventFrames`, never copied numbers) and `onEnd(reason)`. Priority, highest first: a reaction flagged `overridesBlows` (knockdown, death); a blow or Seismic Stomp; a reaction; an action; standing and moving. An action is refused mid-blow, mid-reaction or knocked out, and by default ends the tick he moves.
  - **Warming** the rows it is about to need through `warmRow`.
  - **Motion sets**: `setMotionSet` (called by `HumanPlayer` as the drawn weapon changes; `motionSetOf(look)` picks `unarmed`, `oneHandLight`, `oneHandHeavy` or `twoHand` from the held visual's grip archetype and weight) switches every stance, stride and strike lookup to the rows the weapon's grip and weight play (`src/sprites/art/human/motionSets.ts`); `beginHolster(motion, set, …)` plays that set's draw or stow as an action. No fidgets or level-up gestures with a weapon out.
- **`HumanPlayer`** exposes `handWorldPosition(side)` (the hand tip read off the solved rig of the cell being drawn, so a thrown thing leaves the drawn hand), `seismicStompStampTile()`, and `standBy(reason, spans)` for rows that must be warm before a moment that can come on any tick. His outfit follows his equipment: `onEquipmentChanged` marks it stale and the private `dressInGear` re-dresses him. Every draw of him (`drawHumanSelection`) also holds the resident spans of the motion set in his hand (`residentViewSpans(set)`) warm in every view he is drawn in (`ResidentRows`, `src/sprites/figure/residentRows.ts`), so a snap turn never meets a cold row, even after a menu or a cache flush.
- **Sockets** are not the animator's: they come off the painted figure. `humanSocketsAt(source, row, frame)` (`src/sprites/art/human/sockets.ts`, memoised per figure, row and frame) publishes `mainHand` (his right), `offHand`, `back` and `hip` for the frame the animator chose, solved on the same skeleton the painter draws, and `mirroredSocket` reflects one for a mirrored cell. `HumanPlayer.heldDraw` / `stowedDraw` read them for the frame being drawn. The cat's are `catSocketsAt` (`src/sprites/art/catSockets.ts`: `mouth`, `forePaw`, `back`). The model is in `bipedal-figure`'s `references/human.md` and the `add-gear` skill.
- **The cat** is drawn through the same facing model: `CatPlayer` keeps her own `FacingState`, and `catRowViewOf` (`src/sprites/catViews.ts`, `CAT_VIEW_FALLBACK`) draws a three-quarter facing in her profile, east or west; she is never mirrored (see `add-sprite`).
- **`HumanReactionDirector`** (`src/sprites/humanReactions.ts`) reads the player's state once a tick and asks for the matching reaction row — death over going down and lying out cold, over getting up, over the stumble (paced by how far the shove carried him), over the flinch (front or behind), over the struggle. It never draws him and never changes what happens to him.
- **`humanGestures`** (`src/creatures/humanGestures.ts`) is how systems ask for a gesture outside a fight — Energy Shield cast, drink, pickup, chest open, talk (`HumanTalkDriver`). Systems tell the player what is happening; they never draw him. Where gameplay waits on a gesture (the dome on the palm's landing, the chest's contents once the lid is up) the wait is only as long as the picture, and a refused or interrupted gesture runs the gameplay at once. Systems with their own rows (barricade building, dynamite, repair, placing gym kit) call `human.playAction` directly with the row `human.rowFacing(table)` picks from the view-keyed tables in `humanFigure.ts`.
- **Appearance**: what he wears is read off his equipment as garments (each item's `look`) and applied through `setOutfit('human', …)` (`src/sprites/outfits.ts`), which swaps the active outfit figure and releases the old one's cells; the cat is dressed the same way. What is in his hands is composited between his cell's two layers at its socket: the weapon drawn (`setHumanHeld` swaps to the figure whose right fist is closed on it, keeping the other warm) or the working tool on a swing, resolved through the item's `heldVisual`; an equipped weapon not in his fist is drawn where it rests (`BipedStowedDraw`, the `hip` or `back` socket); `HumanPlayer.drawSelf` hands both to `drawHumanSelection`. The `bipedal-figure` reference (`references/human.md`, "Sockets, the grip and two-layer cells") has the model.
- **`?human`** (`src/scenes/HumanPreviewScene.ts`, `?human=<row>`) plays one row at the game's real pacing at three sizes, beside a live `HumanPlayer` driven through a fixed script; its weapon picker lists every weapon he can hold (read off `ITEM_DEF`), puts it in the live player's hand (the script draws and stows it) and turns the row pane to its rows. `npm run verify:preview-scene` covers it.
- **`?cat`** (`src/scenes/CatPreviewScene.ts`, `?cat=<row>`) loops one of the cat's rows at three sizes, eight real `CatPlayer`s on the eight compass headings (every facing view, labelled with the row view the compass action draws through and whether she faces west), and a live cat walking a full circle. Header pickers step her outfit (every item she can wear, read off `ITEM_DEF`), her working tool and what the compass cats do. `npm run verify:preview-scene` covers it.
- **`?scientist`** (`src/scenes/ScientistPreviewScene.ts`, `?scientist=<action>`) plays Dr. Moult's figure (`src/sprites/art/scientistFigure.ts`) on one action. `npm run render:scientist` runs his gates and renders the sheet, the in-game-size strip, a lineup beside the human and the blind-review image.

The painter, the row table and the gates are in the `bipedal-figure` skill (`references/human.md`).

### Mob levels and tactics

A mob is levelled once, at spawn: `applyMobLevel` multiplies its stats through the curves in `src/creatures/mobLevelScaling.ts` (the only place level math lives), then `applySpawnDifficulty` (`src/core/difficulty/difficultyProfiles.ts`) stamps the profile's reward scale and rolls its tactics traits. Every spawn site calls both, in that order. The curves aim at an HP-share-per-fight target tuned by playtest.

Traits (`src/creatures/tactics/`) are opt-in per creature via `Mob.tacticsEligibility` (default none) and owned by `Mob.tactics` (`MobTactics`). `block` is resolved in `Mob.takeDamageFrom` for every creature; movement traits are queried from the creature's own `updateAI` (`chooseMove` / `disengage` / `claimRiposte`), with `Goblin` as the reference. Tactics read the world through two per-frame publications from `MobUpdateLoop` — the mob grid (`setPackAlertGrid` in `packAlert.ts`) and marked hazard ground (`tactics/markedGround.ts`) — rather than holding a world reference. `verify:tactics` gates them; the rules are P6 in `docs/difficulty-fairness-rules.md`.

## Dialog

`src/dialog/` is where every spoken line in the game lives, and the one place any of it gets rendered from.

- `line.ts` — a `DialogLine` is a value (speaker + paragraphs + advance label), built once per property by a speaker's `LineBuilder` (`speakerLines(id)` for a fixed cast member, `transientSpeaker(name, style)` for one named at runtime) and referenced by every reader — never looked up by a string key.
- `speakers.ts` — `SPEAKERS` (fixed cast, keyed by `SpeakerId`) and `TRANSIENT_STYLES` (voice/reveal/case presets for a runtime-named speaker); `resolveSpeaker` turns either into what the box draws.
- `roles.ts` — role interfaces (`VillagerLines`, `SoldierLines`, `ShopkeeperLines`, `MercenaryLines`, `ResidentLines`) that a script's export `satisfies`, so a missing line is a compile error where the script is written, not a runtime `undefined`.
- `request.ts` — `ConversationRequest` (lines, a reward preview, `ending`, `dismiss`, `haltsWorld`, `anchor`) and `Ending`/`DismissPolicy`/`Choice`/`ConversationTopic`, the data a `Conversation` runs.
- `paginate.ts` — pure, canvas-free page-breaking (paragraph → sentence → word → character), shared by `DialogBox` and unit-tested by `verify:dialog-pagination`.
- `Conversation.ts` — the one conversation panel a scene owns; see `add-ui`.
- `topics.ts` — turns a speaker's `ConversationTopic[]` into a choice row (`topicMenu`).
- `walkAway.ts` — the one rule for when a walk-off surface closes: its talk range plus `WALK_AWAY_MARGIN_TILES`.
- `villagerRegistry.ts` — `VILLAGER_SCRIPTS`/`SOLDIER_SCRIPTS`/`SHOPKEEPER_SCRIPTS`, the role-typed lookup tables generic Briar Hollow code reads a villager through.
- `scripts/` — one file per speaker or scene (`scripts/donald.ts`, `scripts/scenes/defend.ts`, …), each exporting the lines and pools that speaker or scene needs. `verify:dialog-lines` walks every export here and fails on a line nothing ever reads.

`DungeonScene` and `BuildingInteriorScene` each own exactly one `Conversation`: constructed once, ticked once per frame with the player's position, and mounted once on the scene's `UiRoot` through `conversation.surface()`. A system that needs to talk takes that `Conversation` through its constructor deps rather than building a second one. See `add-ui` for the API and `add-quest` for how a quest's dialog is structured.

## Story

`src/story/` holds the story Dave and Caroline tell, and `docs/world-and-story.md` describes the world, both voices, how the story is delivered and how to edit it.

- `storyBeatIds.ts` — `STORY_BEAT_ORDER`, every beat's id in play order, and `StoryBeatId`; `storyBeats.ts` — `STORY_BEATS`, each beat with its lines inline. `defineStoryBeats` (`storyTypes.ts`) holds the table to exactly those ids and checks that every `requires`, `covers` and `afterBeat` id is one of them.
- `StoryDirector.ts` — a pure state machine: `dueBeats(event)` answers which beats play for a `StoryEvent` from the seen set (Dave gets at most `MAX_BEATS_PER_ARRIVAL` per arrival, earlier unseen beats first), `finish(id)` records one. It holds no scene and no rendering; `DungeonScene` threads the run's director by reference like `musicLibrary`.
- `storySave.ts` — the save's run fields `storyBeatsSeen` and `objectivesBriefed` (unknown ids dropped on load) and `persistStoryBeatsSeen`, which writes both into the newest save handed to storage at once, outside the checkpoint.
- `storyPreview.ts` — the `?story=<beatId>` dev route's level, seen set and moment for a beat.
- `src/systems/StoryDelivery.ts` — plays what the director says is due through the scene's cutscene director: Dave's moments (walk-up, beat, then the debrief in the same conversation), Caroline's messages queued for a calm moment (`partyIsEngaged`), and her intel once per objective. `DungeonScene` and `BuildingInteriorScene` each build one; the interior gets the run's director through `InteriorPartyRun.story`.
- Dave's tactics (`DAVE_ADVICE`, `src/dialog/scripts/dave.ts`) and Caroline's intel (`CAROLINE_OBJECTIVE_INTEL`, `src/dialog/scripts/caroline.ts`) are both `Record<AdviceObjectiveId, …>`; `daveAdvice.ts` only picks the objective.

Lore never goes into a quest's or a speaker's own script: it is a story beat.

## EventBus

`src/core/EventBus.ts` — typed pub/sub keyed on the `GameEvents` interface (`mobKilled`, `bossDefeated`, `questStarted/Completed/Failed`, `achievementUnlocked`, `levelComplete`, `healingPotionUsed`, ...). `bus.on(event, cb)` returns an unsubscribe fn; `emit` is synchronous; equipment fires `equipmentChanged` and `weaponSwing` (see "Held equipment and weapons"); `clear()` runs on scene teardown, so subscribers (e.g. `AudioManager.wireEvents`) must re-wire per scene. Prefer wiring sounds to events in `AudioManager.wireEvents` over sprinkling `audio.play` at emit sites.

## Input

`InputManager` only tracks held keys. Every scene with on-canvas UI owns one `UiRoot` (`src/ui/core/UiRoot.ts`; gameplay scenes build it with `createSceneUi` from `src/ui/core/sceneUi.ts`) and exposes it as `scene.ui`. `SceneManager` (`src/core/Scene.ts`) feeds it every pointer gesture through `PointerInput` (`src/ui/core/pointer.ts`, which turns mouse and touch into `down`/`move`/`up`/`cancel`/`wheel` in UI units), offers it every keydown before any gameplay listener, and disposes it when the scene exits. The browser's `click` event is never used.

- **Surfaces.** Each menu, dialog, prompt layer and the HUD is a `Surface` mounted once (`DungeonScene.surfaces()`, and the interior's equivalent). Its band (`world`, `hud`, `panel`, `modal`, `toast`, `system`) and open order make one stack, from which draw order, pointer order, Escape, keyboard focus, `ui.worldHalted()` and `ui.keyboardLocked()` all derive. A scene never keeps its own list of overlays.
- **Pointer.** The topmost region under a press owns the whole gesture and taps on release; a press on no region goes to the scene's `handleWorldPointer(gesture)` — tap-to-move, attack, loot and chest taps, NPC taps, Briar Hollow taps. Nothing else in a scene hit-tests.
- **Keys.** `ui.key` runs key hooks, then the topmost surface's `onKey`, then focus navigation, then Escape. A key no surface consumed reaches `src/systems/GameplayInputHandler.ts`, bound in each scene's `onEnter` via a `GameplayInputActions` callback object; an unclaimed Escape toggles pause, and `isSuppressed` reads `ui.keyboardLocked()`. `SceneManager` marks a key a surface consumed as spent until it is released, and tells `UiRoot` which keys were already held when a new menu appeared (`predatesSurface`).
- **Interaction prompts** are withheld while `surfacesOverHud(ui)` is non-empty.

The full contract is in the `add-ui` skill.

## Render pipeline and UI

**Camera zoom.** `DungeonScene` owns a `CameraZoom` (`src/core/rendering/cameraZoom.ts`): an owner listed in `CAMERA_ZOOM_PRIORITY` asks it each tick to keep a world rect in view (today only the flooded pump room, its `cameraWatchRect` while flooded), and it eases out no further than `MIN_CAMERA_ZOOM`, framing the rect in the part of the screen the HUD's frames, minimap and hotbar leave clear (`clearFrameFor`). The scene publishes the zoom with `setWorldZoom` and draws everything from the world pass to just before `ui.frame` under `ctx.scale(zoom)`; screen chrome inside that stretch goes through `drawUnzoomed`. World-space code measures the view with `worldViewWidth()` / `worldViewHeight()` (screen size ÷ zoom), screen chrome with `viewportWidth()`; a world tap's CSS position is divided by `getWorldZoom()` before the camera is added.

A gameplay scene's `render` draws, in order:

1. The world through `src/systems/RenderPipeline.ts` (ground, Y-sorted entities, effects, fog), then the screen-space world effects in `src/systems/worldEffects.ts` (health vignette, level-up and stat-boost flashes) and world-anchored markers. World text, bars and plates use the painters in `src/ui/world/`; interaction prompts raised here with `drawInteractionPrompt` are only queued.
2. `ui.frame(ctx)`: every open surface bottom to top inside one `ctx.scale(uiScale)` — the `world`-band prompt surface (draws the queued prompts above darkness and fog), the `HudSurface` built from the scene's `HudModel` (unit frames, coin pill, minimap, dock, top band, hotbar), panels, modals, the HUD's `toast`-band overlay (toasts, and the top band when lifted over a scene panel), then system surfaces. The hit regions they register are what the next press is tested against.
3. A few reporters drawn over everything (the reward fly-in to the HUD), and the entity hover tooltip while `!ui.pointerOverUi()`.

Notices go to the toast stack (`MenusKit.toasts.post`), top-of-screen bars to `HudModel.topBand` entries, HUD buttons to `HudModel.dock`. `hudLayout` (`src/ui/hud/hudLayout.ts`) places every HUD piece the same way in the dungeon and indoors, so walking through a door moves nothing.

## AI bridge (optional)

`src/ai/AIAdapter.ts` — singleton bridging to an external LLM server (`AI_SERVER_URL`, default `localhost:3001`) through the SDK's `GameAiClient` (`@rscarbel/game-server-llm-sdk`); off when disabled (`AI_ENABLED` in `.env`) or no one is signed in. It authenticates with a short-lived player token from the game server's `/api/ai-token` (no AI credential is in the bundle; see `dev-workflow`), streams the context builder's output, sends player chat as `player_message`, and answers every `ai_action` with an `action_result` (run, refused by the governor or the player's AI intensity, or expired while paused). The AI Intensity setting (`src/ai/aiIntensity.ts`, persisted in `Settings`) becomes `context_set`'s `policyMultiplier` and `allowedSeverities`. What the player sees lives in `AIChatFeed` (streaming typewriter, typing indicator, reply choices, opinion flashes, "intervened" lines, the online/degraded/offline status) and is drawn by `src/ui/hud/aiPanel.ts`, mounted by each gameplay scene through `aiAdapter.surfaces(...)`. Offline, Caroline answers from `CAROLINE_FALLBACK_LINES` (`src/ai/characters/fallbackLines.ts`). `npm run verify:ai-transport` gates the adapter against a fake client. `setOutboundListener` sees every message the adapter actually sends; the dev-only replay recorder (`src/dev/aiReplayRecorder.ts`, `?ai-record`) and `npm run ai:replays` record AI replay fixtures through it (format in `src/ai/replay/aiReplayFormat.ts`; see `dev-workflow`).

What the AI can do lives in `src/ai/actions/`. `registry.ts` is the one list: each `AIActionDef` declares its parameters (typed fields from `schema.ts`, which are both the JSON Schema shown to the model and the parser for what comes back), its policy (cost, cooldown, severity, context flags, characters), its per-floor limits and budget draw, and its executor. The tool definitions (`generateAIToolDefinitions`, re-exported as `AI_TOOLS` by `aiTools.ts`) are generated from it, with mob names from the floors' spawn tables and the kind registry (`MOB_KINDS`) and item names from `ITEM_DEF`. `executeAIAction` validates a call, asks the `ActionGovernor` (`governor.ts`: the fairness rules for AI actions — no spawns or harm in menus or while a crawler is under 25% HP, no stacking stat changes, cooldowns, per-floor caps and depth-scaled budgets) and runs it, returning `{ ok, detail, indicator }`; `dispatch.ts` parses both `ai_action` wire shapes and holds calls while the game is paused. Scenes hand actions an `AISceneContext` (`types.ts`): a required core plus optional capabilities (toasts, achievements, audio, the collapse clock, the camera spotlight) that an action reports unavailable when a scene leaves one out. A new action is a new `AIActionDef` in one of the group files; `npm run verify:ai-actions` checks every action's schema against its tool definition and fuzzes calls through the governor. The actions that deal with the player directly (`interactions.ts`: `grant_achievement`, `ask_player`; `challenge.ts`: `offer_challenge`) reach the screen through the scene's `AIInteractionStage` (`src/ai/interactions/`, offered as `AISceneContext.getInteractions`): it shows questions and challenge offers as surfaces and emits each outcome on the bus (`playerAnswered`, `challengeAccepted`/`Declined`/`Completed`/`Failed`, `aiAchievementAwarded`). Challenges are templates with bounded parameters (`src/ai/interactions/challenges.ts`) interpreted by `AIChallengeSystem`; AI-written achievements are filed on `AchievementManager` beside the built-in ones and paid, like every award, through the scene's `AchievementAwards` (`AISceneContext.getAwards`). AI-spawned mobs go through the same `spawnMob` funnel (`src/levels/spawnFunnel.ts`), levelled once inside the floor's band.

What the server knows is built in `src/ai/context/` by `AIContextBuilder`, which the adapter owns for the page's lifetime and each gameplay scene binds with `aiAdapter.bindScene(sceneCtx, bus, source)` (both `DungeonScene` and `BuildingInteriorScene`, through their `createAIContextSource()`; unbind with the scene's own bus). It produces `context_set` (session facts, the boolean flags tool policies name — `SESSION_FLAG_NAMES` in `sessionContext.ts` — and the derived player profile), `state_snapshot` (full, then RFC 7386 merge patches, at most once a second) and `event_log` (`eventMapping.ts` maps bus events to summaries, importance and `witnessedBy`; kills roll up per fight, dodges are sampled). A new bus event the AI should hear about gets a handler in `eventMapping.ts`. `transport.ts` hands them to the SDK client (`SdkContextTransport` keeps the whole state the patches describe, since the client computes its own patches). Event importances come from one table, `EVENT_IMPORTANCE` in `eventImportance.ts`, which `ai:sync` also uploads as hints. The world bible (`worldBible.ts`) and the characters (`src/ai/characters/`: identity, voice, traits, goals, allowed tools, knowledge scope) are exported for syncing to the server. `npm run verify:ai-context` gates it.

## Docs and plans

`docs/` holds two different kinds of file, and they have opposite lifetimes.

Durable reference — describes the shipped system, is kept and maintained:

- `docs/town.md` — how the third floor's town is generated, rendered and tuned
- `docs/asset-management.md` — lazy sprite/sound loading, per-floor eviction, declared coverage, surface owners and byte limits, perf measurement
- `docs/difficulty-fairness-rules.md` — the P1-P6 fairness rules (curves, telegraphs, tactics) and the target-feel bands
- `docs/world-and-story.md` — the world premise, Caroline and Dave, their voice rules, how the story is delivered, and where every story line lives

Every other file in `docs/` is an implementation plan — usually named
`*-plan.md`, occasionally not — meaning scaffolding written for an agent to
execute, and DELETED once the work ships. Never cite a
plan, a plan phase, or a plan section number from code or from a skill — the
pointer is guaranteed to rot.

Never cite a source line number either — not from code, and not from a plan.
It rots on the next edit to that file, and a plan is read by an agent that will
trust it, so a stale `Foo.ts:317` sends that agent to the wrong code. Point at a
file, a function, a class, a constant, or a distinctive quoted fragment; those
survive edits and can be found by grep. When writing a plan, cite symbols for the
same reason.

## Design debt

If this work turns up hacky code, a fragile coupling, or a design that will make the next change harder, and it is beyond your task, record it in `docs/design-debt.md` (rules and entry shape are at the top of that file). Before building on a system, check that file for entries about it and honour their **Until then** lines.
