---

## 1. Goal

Replace the six hand-drawn tree PNGs on the Level 3 overworld with a **procedurally generated, offline-baked tree sprite family** that:

1. **Looks like one forest** — many distinct trees, one shared palette/canopy engine, so variety never reads as "assets from different games".
2. **Is taller than one tile** — the base occupies one tile; the canopy climbs three tiles above it.
3. **Sorts correctly against entities** — the player walks *behind* a tree whose base is south of their feet, and *in front of* a tree whose base is north of their feet. (Today trees always draw behind everything — see §3.)
4. **Is destructible** — significantly tougher than a crate/barrel.
5. **Burns.** Every magic missile that hits a tree has a **10% chance to ignite it**. A burning tree burns down to a **black charred husk** that is then trivially destroyed.
6. **Hurts the player on contact while burning** — standing adjacent deals damage immediately, and applies the existing `burn` status once the player has been in contact for **1 second**.
7. **Reacts to explosives** — dynamite **always destroys** every tree in its blast radius and **ignites** the trees in a ring just outside it.

---

## 2. Non-Goals (do NOT build these)

- **Ambient fire spread between trees.** Only explosives ignite neighbours. A burning tree does *not* set its neighbours alight on its own. Leave a single well-named hook (`TreeSystem.igniteRadius`) so this can be added later, but do not call it from the burn tick.
- **New audio files.** Reuse existing `SoundId`s only. Do not add `.mp3` assets.
- **Burning mobs.** Trees damage *players* on contact. Mob-vs-fire is out of scope.
- **Trees on any floor other than 3.** `TREE` (tile type 13) is only generated by `OverworldGenerator`. Do not add trees to dungeon floors.
- **Persisting tree damage across save/reload.** Tree state is per-session.
- **Reworking `grassy_weed` / `dirt_patch` / any other nature asset.**
- **Animated idle sway.** `idle` is a single static frame. (Sway would force every tree tile out of the static path every frame; not worth it at forest density.)

### 3.4 Sorting — the core defect
`src/systems/RenderPipeline.ts:56-57, 238-256`:
```ts

…
e.sortY = isTree ? ty - TREE_SORT_DEPTH_OFFSET : ty * TILE_SIZE + sortYAnchorPx;
```

Trees get a sort key in **tile** units, offset by −100000, so **every tree sorts before every entity**. The player therefore always draws on top of a tree, never behind it. `isTree` (`GameMap.ts:158, 2114`) is the only type-specific flag on `DecorationTile` and exists solely to feed this branch.

Every other decoration uses the correct key: `ty * TILE_SIZE + sortYAnchorPx`, where `sortYAnchorPx = (frameHeight - tileY) * (TILE_SIZE / tileScale)` (computed `SpriteLoader.ts:246-255`, read via `getSortYAnchorPx(tileTypeId)`).

Because no tree manifest entry declares `tileTypeId`, `getSortYAnchorPx(TREE)` returns `undefined` and `GameMap.ts:2115` falls back to `ts`. Likewise `decorationTileExtentsPx` (`TileRenderer.ts:418-442`) misses and falls back to `unregisteredDecorationExtents(ts)` = 1 tile in every direction. **A 3-tile-tall tree will be clipped/culled unless a manifest entry declares `tileTypeId: 13`.**

`BuildingInteriorScene.ts:1493` already uses the generic formula and has no `isTree` case — no change needed there.

## 5. Design Decisions (settled — do not re-litigate)

### 5.1 New directory, not `nature/`
Trees go in **`src/images/environment/trees/`** with their own `manifest.json`. Reason: `writeSheets` replaces a directory's entire manifest, and `nature/manifest.json` also holds `grassy_weed` and `dirt_patch`, which would be destroyed. This also matches the `townscape/` vs `towns/<town>/` folder discipline already in the repo.

### 5.2 One geometry envelope for every tree
Every tree sheet shares **identical frame geometry**:

| field | value | meaning |
|---|---|---|
| `tileScale` | `32` | matches `TILE_SIZE`; 1:1 blit, no rescale |
| `frameWidth` | `96` | 3 tiles — 1 tile of canopy overhang each side |
| `frameHeight` | `128` | 4 tiles — base tile + 3 tiles of trunk/canopy above |
| `tileX` | `32` | anchor tile is the middle column |
| `tileY` | `96` | anchor tile's top edge; `frameHeight - tileY === 32` ✅ |

**Why one envelope:** `tileTypeId` is a 1:1 map to geometry in `SpriteLoader` (`_tileSortYAnchorPx`, `_tileSpriteOverheadPx`, `_tileSpriteExtentsPx` are all keyed by tile-type id, last write wins). Shorter species simply leave transparent pixels — transparent pixels are free, a clipped baked frame is permanent.

**`tileScale` stays 32, not 64.** The town-art lesson applies: painters that mix fixed-pixel constants get silently thinned when baked at 64 and halved at draw time.

### 5.3 Exactly one key declares `tileTypeId: 13`
Add `"tileTypeId": 13` to **one** canonical tree entry (`tree_oak_a`). This is what makes `getSortYAnchorPx(TREE)` return 32 and `getSpriteExtentsPxForTileType(TREE)` return `{left:32, right:32, up:96, down:0}` instead of the 1-tile fallback. Declare **no** `blockedRegions` — walkability is already handled by `NON_WALKABLE_TILE_TYPES`, and a `blockedRegions` entry would start blocking canopy tiles.

`writeSheets` must be able to emit `tileTypeId`; if it cannot, extend `SheetSpec`/`manifestEntry` in `scripts/townSheets.ts` to carry an optional `tileTypeId` rather than hand-editing the generated JSON.

> ⚠️ **Perf checkpoint (Phase 3):** `up: 96` equals `OVERSIZED_DECORATION_EXTENT_TILES * TILE_SIZE` exactly, and the test is `> limit`, so trees stay in the *modest* row buckets and widen `_modestDecorationExtents.up` to 96 px for **every** decoration's row scan (`GameMap.ts:190-199, 2008-2054`). Measure the frame time in a dense forest before and after. If it regresses, do **not** shrink the tree — bump the up-extent to 97 so trees fall into `_oversizedDecorations` instead, and re-measure.

### 5.4 Species and variants — "varied, but one forest"
**3 species × 4 variants = 12 sprite keys.**

| species | key prefix | silhouette |
|---|---|---|
| oak (broadleaf) | `tree_oak_a`…`_d` | wide, lobed, heavy crown, thick forking trunk |
| birch (slender) | `tree_birch_a`…`_d` | narrow, tall, pale bark, airy crown |
| pine (conifer) | `tree_pine_a`…`_d` | conical, layered boughs, straight bole |

Cohesion rules — **all twelve share**:
- one `FOLIAGE_RAMP` and one `BARK_RAMP` per species, all three species sampled from a single master palette so hues sit within a narrow band;
- one canopy engine (same clump/leaf-mass primitive, same light direction — **upper-left**, matching every other prop in the repo);
- one `contactShadow` treatment at the base;
- one silhouette budget (crown never exceeds `frameWidth`, base always centred on the anchor tile).

Variation comes from seeded parameters only: trunk lean, crown radius, clump count, branch fork angles, foliage-value jitter. Each variant uses a fixed literal seed (`makeRng(TREE_SEEDS.oak_a)` etc.) so re-runs are byte-identical.

### 5.5 Spatially coherent species placement
Species must be coherent so a forest reads as one wood, while individual trees still differ:
- **Species** from a low-frequency hash of `Math.floor(tx / GROVE_SIZE_TILES)`, `Math.floor(ty / GROVE_SIZE_TILES)` with `GROVE_SIZE_TILES = 24`.
- **Variant** from the existing per-tile hash (`Math.imul(tx, 2654435761) ^ Math.imul(ty, 2246822519)`) mod 4.

No per-tile storage; stable across frames and re-bakes, exactly like today.

### 5.6 Sheet rows (states)
Six rows per key, max 6 frames wide:

| row | state | frames | content |
|---|---|---|---|
| 0 | `idle` | 1 | healthy tree |
| 1 | `damaged` | 1 | bark gouged, boughs snapped, thinned crown |
| 2 | `burning` | 6 | flames climbing the crown, crown still green underneath |
| 3 | `burning_late` | 6 | crown mostly consumed, trunk alight, embers |
| 4 | `charred` | 1 | black skeletal husk, no leaves, no flame |
| 5 | `felling` | 6 | collapse — trunk topples, debris, dust/ash puff |

Plus a **shared** `remains` decal. Do **not** give each tree its own remains row; emit one `tree_remains.png` (single frame, boxed geometry like the props' remains) reused by all twelve — a stump and scattered ash reads the same regardless of species, and twelve near-identical rows is waste.

> `felling` and `remains` mirror the props' `shatter` / `remains` contract so `DestructiblePropSystem`'s animation timing constants (`SHATTER_FRAME_COUNT = 6`, `SHATTER_FRAMES_PER_STEP = 5`) can be mirrored rather than reinvented.

### 5.7 Burn lifecycle
```
idle ──(missile 10% | explosion ring)──▶ burning ──▶ burning_late ──▶ charred ──(any hit)──▶ destroyed
  │                                                                                             ▲
  └────────────────────────(enough melee/missile damage)────────────────────────────────────────┘
```
- Burning **never destroys the tree by itself** — it always terminates at `charred`. The user asked for "a black, charred object that could be easily destroyed".
- A charred husk is permanent until something breaks it.
- Fire cannot be extinguished.
- Igniting an already-burning or charred tree is a no-op.

### 5.8 Tuning constants (starting values — tune in Phase 7)
Put these in `TreeSystem.ts` as named constants. No bare literals.

| constant | value | rationale |
|---|---|---|
| `TREE_HP` | `28` | ~4.5× a crate (6) — "significantly harder" |
| `TREE_DAMAGED_HP_FRACTION` | `0.5` | switch to `damaged` art below half HP |
| `CHARRED_TREE_HP` | `3` | "easily destroyed" — under a crate |
| `BURNING_FRAMES` | `420` (7 s) | time in `burning` before `burning_late` |
| `BURNING_LATE_FRAMES` | `300` (5 s) | time in `burning_late` before `charred` |
| `MISSILE_IGNITE_CHANCE` | `0.10` | per the request |
| `EXPLOSION_IGNITE_RING_TILES` | `2` | ring outside `DYN_RADIUS` that catches fire |
| `TREE_CONTACT_RADIUS` | `TILE_SIZE * 1.1` | centre-to-centre; "standing next to it" |
| `TREE_CONTACT_DAMAGE_INTERVAL` | `30` (0.5 s) | contact damage cadence |
| `TREE_CONTACT_DAMAGE` | `2` | per tick |
| `TREE_CONTACT_BURN_DELAY` | `60` (1 s) | contact ticks before `makeBurn()` — per the request |
| `TREE_FLAME_FPS` | `10` | burn animation rate |
| `TREE_COIN_SPREAD` | `2` | drop scale (floor 3 → 3–5 coins) |

**Contact-damage semantics** (read carefully — this is the exact request):
> "Touching the tree as it is burning should hurt the player. Standing next to it so the player is 'touching' should cause them to take damage and then get the burned status after 1 second has passed."

So: damage starts on the **first** contact tick, and `makeBurn()` is applied once the accumulator reaches `TREE_CONTACT_BURN_DELAY`. The accumulator resets to 0 the moment the player breaks contact (acid-puddle pattern). Damage source: `{ kind: 'environmental' }` — or a `'mob'`-shaped source is *wrong* here since no mob is involved. Use `{ kind: 'environmental' }` and confirm `Player.takeDamage` treats it as undodgeable; if it does not, that is a real gap — note it in the Journal and add the handling.

### 5.9 Where tree state lives
Mirror the props exactly:
- **Volatile HP + burn timers:** `TreeSystem`'s `Map<string, TreeState>` keyed by `tileKey(tx, ty)`, created **lazily on first hit or ignition**. A 280×280 map with 30 forest blobs must cost zero until something is touched.
- **Renderer-visible stage:** on the tile itself (`TileContent`), because `drawDecorationTile` is a pure tile renderer with no access to systems — exactly how `TORCH`/`BRAZIER` read `structure[ty][tx].damageStage` at `decorationTiles.ts:663-698`. Add:
  - `treeStage?: number` — `TREE_STAGE_HEALTHY | DAMAGED | BURNING | BURNING_LATE | CHARRED`
  - `treeBurnFrame?: number` — animation cursor, advanced by `TreeSystem.update()`

  and a `treeSpriteState(stage)` helper next to `propSpriteState` in `src/map/tileTypes.ts`.
- **Destruction** follows `breakProp`: `tile.type = tile.groundType ?? inferFloorType(...)`, delete the tree fields, `gameMap.markTileDirty(tx, ty)`, spawn debris + `loot.addLoot(...)`.

> ⚠️ `TileGrid.set` (`src/map/town/tileGrid.ts:104-109`) deletes any recorded `groundType`, and `paintForests` uses `grid.set` — so a felled tree will usually fall back to `inferFloorType`. Ground for a tree tile is forced to `'grass'` (`groundMaterials.ts:166-173`), so verify the revealed tile is grass and not a wrong material. If it is wrong, fix it in `groundMaterials.ts`, not by special-casing the renderer.

### 5.10 `TreeSystem` public API
Deliberately mirrors `DestructiblePropSystem` so the call sites read the same:
```ts
tryMeleeHit(attacker, range, damage): boolean
tryAreaHit(attacker, radius, damage): boolean
tryProjectileHit(x, y, radius, damage, owner): boolean   // returns true if a tree was struck
destroyInRadius(x, y, radius, owner): boolean
igniteAt(tx, ty): void
igniteRadius(cx, cy, radius): void                        // the explosion ring; also the future spread hook
drainFelled(): number                                     // for the audio drain in DungeonScene
update(ctx: SystemContext): void
render(ctx, camX, camY): void                             // flames, embers, contact glow
```
`tryProjectileHit` returning `true` is what lets `CombatSystem` roll the 10% ignite and stop the missile.

## 7. Review Gate — MANDATORY, EVERY PHASE

**No phase is complete until its review gate has closed.** Do not batch phases and review once at the end.

Run this loop at the end of every phase:

1. Ensure `npm run typecheck`, `npm run lint`, and `npm run format` are all clean **before** requesting review. Do not send a reviewer broken code.
2. Spawn an **independent reviewer agent** (`Explore` or `general-purpose`) that has **not** written any of the code. Give it:
   - the phase's diff (`git diff` / `git diff --staged`, or the explicit file list),
   - the relevant sections of this plan (goal, §2 non-goals, §5 design decisions, the phase's checklist),
   - `CLAUDE.md`'s rules: **no `as` casts, no `!` non-null assertions, no `any`, no magic numbers, no "what" comments, prefer `src/ui/` helpers for UI chrome, prefer named variables over terse one-liners.**
   - this instruction: *"Report only substantive defects: correctness bugs, type-safety violations, violations of the stated design decisions, missed requirements, performance regressions, dead code, or missing wiring. Do NOT report nits, style preferences, opinions, or anything outside the stated scope. If you find nothing substantive, say exactly: NO SUBSTANTIVE FEEDBACK."*
3. Triage each item as **genuine** or **not genuine**. An item is **not genuine** only if it is truly (a) a nit, (b) out of scope per §2, or (c) a matter of opinion with no correctness or requirement impact.
4. **Implement every genuine item.** Journal the ones you reject, with the reason.
5. **Request review again** — a fresh reviewer, given the updated diff.
6. **Repeat until a review returns `NO SUBSTANTIVE FEEDBACK`.** Only then tick the phase's Review Gate box.
7. Record in the Journal: how many review rounds it took, what was fixed, what was rejected and why.

> If reviewers ping-pong (round N+1 reverses round N), stop and write both positions in the Journal for a human to settle. Do not loop indefinitely.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Taller trees widen `_modestDecorationExtents` and slow every decoration row scan | Explicit perf checkpoint in Phase 3 (§5.3); fallback is to push trees into `_oversizedDecorations` |
| A Y-sorted tile registered in only one of the two registries renders as **bare floor**, and typecheck/lint both pass | `TREE` is already in both — do not remove it from either. Re-check `TileRenderer.ts:71-94` and `GameMap.ts:166-188` if trees vanish |
| Twelve trees look like twelve games | One palette, one canopy engine, one light direction (§5.4); Phase 7 judges the *forest*, not the tree |
| Non-determinism in the generator makes diffs meaningless | Fixed literal seeds; Phase 2 runs the generator twice and requires a clean `git status` |
| A new PNG that no manifest names is silently dropped from the shipped build | Phase 8 verifies against `scripts/shipped-assets.js` |
| `drawDecorationTile` has no access to systems, so burn animation can't read `TreeSystem` | Stage + frame cursor live on the tile (§5.9), mirroring how `TORCH`/`BRAZIER` read `damageStage` |
| Burning-tree scan becomes O(forest) per frame | Iterate the burning-state `Map` only; never scan the grid |
| A felled tree reveals the wrong ground material | Phase 4 verifies; fix in `groundMaterials.ts`, not the renderer |
